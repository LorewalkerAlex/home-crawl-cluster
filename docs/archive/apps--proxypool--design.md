## 基于官方能力的收缩建议（2026-10-25）

用户要求评估 0.7 和重新优化 Proxypool。升级资料与发行渠道的实际差异见 [官方复核](../crawlab-official-review.md)；目前建议保留 0.6.3，不修改部署文件。以下作为新的助手推荐稿，保留用户功能需求，取代自建内容一律默认存在的写法；不是已选定新数据链路。

### 运行与代码边界

1. Crawlab 继续使用既有 Master、专用平台 MongoDB 和 Worker；它负责程序、文件、Schedule、节点和原生 Task／日志／结果界面。
2. Proxypool 服务端先用一个业务进程，内部仍分 M03 来源配置接入、M04 选测与发布、M05 导入／质量／获取／生命周期等独立代码模块；不为各模块增加独立常驻发布、接收或恢复容器。
3. Worker 运行标准 Scrapy 来源程序及 aiohttp 小批测试程序，公共适配只做必要输入／输出，不先建通用 runner。
4. M06 仅补目标设置、代理质量／获取、业务完整性和必要的来源健康／容量视图；节点、代码、平台任务和日志直接用 Crawlab，不复制一整套。

### 来源：平台登记和原生 Schedule 为主

建议每个来源对应明确的 Crawlab Spider 记录，使用固定的审核入口，例如 scrapy crawl source_a。同一套 Scrapy 项目可有多个网站 Spider，不要求每网站一套独立运行环境。先测试网站代码，再登记和上传，保持显式允许清单，不因目录里多一个文件就自动执行。

2026-10-28用户补充后，来源发布统一经过M03的抓取轮次入口：先由M05检查轮前数量，超阈值时按最低测试次数门槛筛选、按讨论中的总分末尾清理轮前超量；完成后才发布本轮，等待本轮任务及回传收尾再考虑下一轮。用户允许轮内超量及评分小幅变化，来源少且有timeout，不增加单轮新增额度或池数量硬挡板。周期触发仍优先复用Crawlab，但各来源独立Schedule不得绕过该轮次入口；具体触发方式、次数口径、候选不足及轮次结束细节后续确定，不先建设第二套通用调度器。完整边界见docs/protocol.md的抓取轮前容量清理。确有数据库内容驱动的后续任务时再补具体发布逻辑。前端执行状态直接关联 task_id，来源健康可由本轮摘要表达；摘要作为标准结果数据，不强制每个网站自己写 start／finish HTTP 回调。

### 测试：业务选测与平台执行分开

M04 仍按近期真实使用、新代理、最新失败等业务条件分页选测，避免重复选择有效在途组合；构造同目标配置 revision 的有限小批。M05 先保存固定批次、小任务和成员，再通过原生 API 发布；单个代理＋目标仍有独立成员 ID，不再每项启动平台进程。

Worker 读取小批输入快照，按配置异步并发测试；每项输出 check_result，带稳定成员／观测身份，分包交给匹配版本的 SDK。正常收尾补小批摘要，输入不靠大段命令行 JSON 传输。批大小示例 100 继续配置化，不把它当 HTTP 并发量；节点任务槽与内部请求并发分别限制。

### 候选 A：原生中转与业务事务

候选 A 为 Worker → SDK／Pipeline → Crawlab 原生 MongoDB 结果 → M05 有界导入 → SQLite。这样复用现成传输、任务关联和结果 UI，并利用已经存在的平台 MongoDB；不用预先开发完整 Worker 状态回调体系。这是候选 A 的取舍说明，不代表它优先于或取代候选 B。

M05 只查询已知待处理任务，不轮询整个平台全部历史。首版可在任务终态后，按页导入并根据固定成员／摘要核对完整性；相同记录去重，未收齐不能只因 finished 就成功。原生结果异常或迟到也有有限核对期限，超期明确结算未完成部分；需要中途业务进度时再增加受限增量导入，不先做全量实时同步。

来源发现按端点幂等合并；测试与真实使用统一按观测身份去重、保存有限样本、更新受影响组合及业务进度，同短事务提交。M05 完成之后才称业务入库完成。测试失败是已处理结果；Worker 崩溃／缺结果不虚构代理失败。部分已提交的有效结果保留。

不建议直接把原生 SQLite 数据源指向 M05 主库：本次核对的 SQL 适配逐条插入且错误可被继续处理，不能满足幂等、合批和质量／完成事务，也会改变唯一写入入口边界。原生 SQLite 的支持事实保留，可用隔离空库验证，不因此否定用户选择 SQLite。

该路径有代价：平台暂存与 SQLite 各有写入，存在导入延迟，并需要平台结果／日志的有限保留。仅导入完成、已核对的中间结果才可按所选版本支持的方式清理；尚未验证原生全局 TTL／容量参数，不承诺删 Task 就删了所有结果。若隔离验证表明该路径不适合，再采用单一最小业务上传入口，不同时做两套默认回传。

2026-10-26用户补充：状态必须兼顾代理获取，而非只服务自测。三种测试成员状态仍是建议，不能代替按目标的质量；自测与真实反馈共同更新质量，取代理依据有效证据与排名，待测试标记仅用于防重复选测。具体共同状态和缓存建议见 [协议](../protocol.md#自测代理获取与真实反馈的共同状态2026-10-26设计补充)。

### 获取、评分、批写和退出

用户的目标候选队列保留：读取已维护的优质且未过期组合，在相近质量内随机 pop；目标／revision、每队列条数、TTL 和总内存有界，空池退避，相关退出／配置变化及重要质量变化使旧候选失效。实际调用反馈必须进入 M05 的同一观测入口，不能因缓存获取而省略反馈身份。

M05 继续采用唯一写入口、有限队列及短事务；收集窗口不占写锁，条数／字节／最长等待任一先到即 flush。10s 是用户示例，状态及时提交、请求超时和结果可见延迟需要统一，不能所有 API 固定等满窗口。

评分沿用近期有限样本及标准 Wilson 下界推荐，速度次级；仅重算受影响组合，获取时不扫描全样本。目标证据过期与全局代理退出分开，不因一次或连续失败直接暂停／删除，不保存逐代理来源。窗口、阈值、退出规则和实际长期时间字段仍待 M05 审阅。

本轮没有新增 Redis、消息总线、工作流引擎或第二套通用状态库。管理后台和业务进程分开，业务模块仍可在同进程维护明确边界，节省常驻内存与运维成本。

### 完成状态和数据流

来源执行开始后抓取／解析，完成后提交数据及摘要，M05 校验、按端点唯一键合并、保存入库统计并确认。抓取结束可以展示为待入库／入库中，不能在提交前显示整轮业务成功；全部有效端点已存在而新增数为零仍可以成功。部分页面失败时保留有效产出并显示部分完成；合法零产出、解析异常与入库异常分开。代理表仍不保存来源映射，来源运行只保存有限统计。

M03／M04 控制逻辑状态转换，M05 承担唯一持久写入口，不能由 Worker 和数据库分别覆盖同一最终状态。以本次 run_id／小任务 ID 关联原生 task_id，重复开始不重置时限，重复结果不重复计分，旧轮不能改新轮。结果保存、必要进度及最终业务确认在同一短事务结算，UI 只读取事实，不做业务状态接收终点。

测试的大批次包含有限个小平台任务，每个小任务包含固定测试成员；任务内部使用受限 aiohttp 并发，结果可分小包及时提交，不必等 100 项全结束才回传。M05 按固定清单累计已处理成员，小任务和父批次逐级汇总；测试失败是已处理，不等于任务执行失败。Worker 被杀无法保证回调，现有维护循环按原生状态和有限期限收尾无反馈项，不合成代理失败；正常成功确认不能越过未提交结果。

### 批写窗口和缓存边界

用户提出从首个写请求开始等 10s 合批。建议将它解释为可配置的最长收集时间：从第一项入队起计，不被后续请求延长；记录数／字节先到则提前 flush。等待在 SQLite 事务外；真正写入才开短事务，提交后才确认。入队／等待必须有界，满时背压。开始、停止及最终状态等需要及时可见的控制操作触发尽快 flush，仍走同一写入口；不要求每个代理单独提交，也不让所有操作固定等待 10 秒。Worker HTTP 超时／重试须覆盖该等待，合批不使未提交内存数据具备持久性。

缓存按目标及配置 revision 隔离，容量、TTL、活跃目标数／总内存均有上限；实际可用期不超过所含质量证据的有效期。目标停用／改规则、代理退出和重要质量变化在提交后使相关旧候选失效；若分进程而暂只用 TTL，则须明示允许的陈旧窗口，不能承诺立即生效。10s 入库等待与缓存 TTL 会叠加影响可见时效。缓存空时短暂退避，不能为无候选反复高频查库；补充同目标请求合并，避免并发重复装载。

分发后需要真实调用反馈与去重。可在获取候选批时一次登记分发批次及成员，pop 返回关联 ID，未使用成员不计失败，以降低逐次分发写入；调用方绑定、使用截止及反馈期限仍待 M05 确认。不能只因候选来自缓存就丢掉实际使用结果，也不将候选缓存当独占租约。

### 评分、选择和退出

M05 继续负责真实自测／使用观测的统一去重、有限近期样本及受影响组合的质量重算；同一写批内只重算受影响的代理＋目标配置组合，不每次获取全表算分。沿用此前推荐的 Wilson 下界处理成功比例和样本量，成功耗时作次级参考；具体窗口／条数／门槛未逐项确认，分数不保证未来成功率。无证据新代理先预热，不把抓取发现当访问成功。旧证据到期即使没有新写入也不能一直有效。

不建议在全部分数层级中无差别打乱：它会使高低质量以同等机会被选中。建议先取证据有效的优质候选，在相近质量范围内随机／轮换；池不够时明确返回不足，是否扩大质量范围另议，不默默降低质量。

代理退出分层处理：某目标质量证据失效只影响该组合，目标停用不删除其他目标成绩，全局代理删除由生命周期模块按容量和明确规则决定，并清理关联有限数据及缓存。保留用户此前不按单次／连续失败直接全局暂停或删除的约束。实际全局退出条件、近期时间字段与配额留 M05 讨论，不自动决定硬编码天数。

资源取舍：小平台任务减少子进程／日志数量，但批过大降低节点间分配弹性；配置批大小、HTTP 并发、在途／发布速率和超时。内存获取队列减少候选读取，有活跃目标数×每目标条数的容量成本；写队列有字节／条数／等待上限。SQLite 采用单写及索引当前汇总，统计按有界分页／定时缓存读取，不在每次前端刷新做全样本扫描。当前未实测，也未因此增加 Redis 或拆分进程。

## 必须自写的业务方法

## 三条主要链路

### 来源采集

来源登记并启用 → M03 按触发规则选择并发布 Crawlab 任务 → Worker 复查本轮权限及启停 → 标准 Spider 请求与 parse → 公共 Pipeline 校验并回传 JSON → M05 按端点合并并保存来源运行摘要 → 提交后前端可见。固定周期可由 M03 配置原生 Schedule；不另造通用调度器，不保存代理来源映射。

原生 Stats 默认内存保存，关闭时的统计桥接仍需实现和验证。进程被杀没有 run_summary 时，应按平台异常展示，不能把缺少统计当成零错误成功。每页请求状态可用标准响应／错误事件记录，日志直接关联 Crawlab。

### 测试与反馈

用户明确测试闭环：M04测试系统从M05取得本轮需要测试的代理＋目标组合，M05在返回前持久标记为待测试，再由M04发布到Crawlab；Worker处理后直接回传M05，M05更新状态和结果。下一轮重新向M05获取需要测试的内容；Worker不自行重新安排或重跑测试任务。选测规则必须考虑已安排状态，避免重复发布。

建议以testing.reserve_checks替代含糊的先查后标：选取及占用同一SQLite短事务提交，M04随后在事务外发布；Worker按固定身份执行一次网络尝试并直接回传M05。回传结果、质量及对应成员状态同事务更新；已执行失败也算处理，无反馈不算代理失败。下一轮排除有效在途组合，按到期策略重新选取。

需要测试的规则、少量当前字段、发布不确定／过期回收、迟到反馈及资源限制的建议唯一维护在 [主动测试协议](../protocol.md#主动测试任务)，不在此另列第二套默认值。用户尚未确认具体超时、重试传输、状态名和签名；开始／结束回调不自动套用来源三动作。

真实调用的report_usage仍进入统一观测入口，既影响评分，也影响后续选测；仅分发未使用不计失败。来源请求是否使用框架有限重试另议，不据此让测试Worker自行重测。

### 跨设备解析

A 抓取 → 原文完整保存到服务器文件目录 → 发布只引用文件 ID 的解析任务 → B 读取原文并复用提取规则 → 同一结果入口导入。

这一步仍是需求，但后于基本链路验证。只补具体文件上传读取和解析程序，不为所有业务定义新通用 RawDocument／Artifact 平台。复杂 Spider 的后续 Request 要按来源处理，不宣称任意 parse 都可直接离线回放。

## 评价与主动测试

本轮按用户要求给出完整推荐方案：以现成 Wilson 下界处理成功比例和样本不足，再用固定近期窗口控制旧证据；速度独立用于稳定性相同时排序。该方案替代仅列待定项的版本，但不恢复自创衰减公式或连续失败暂停。

窗口、自测免测与复核间隔、预算、候选选择、网络范围以及过期处理统一定义在 [存储方案](../../apps/proxypool/storage.md)。只有实际结果才提供证据，分发时间不用于冒充最近成功。目标规则改变后按 revision 隔离，execution_error 和没有执行的成员不计代理失败。

## 原生结果的验收门槛

先验证一个 Spider 与一个普通 Python 测试程序：结果能保存、按任务查询、分页完整、异常结束行为可解释。SDK 与平台分支的通道存在差异，必须选择配套版本。

导入按业务身份去重，不能只认为每个新增平台结果行都是一次新的真实访问。任务 finished 之后仍要核对结果是否已可读、是否有迟到记录；小规模可重复核对并 upsert，具体策略随 API 联调确定。

原生路径若不满足需求，再比较受控业务上传与 JSONL 导入的最小补充方案。此验证未完成前，不承诺自动重试、持久确认或恰好一次处理，也不为假设性缺口先搭建全套替代系统。

## API 范围

业务 API 只覆盖来源与目标 CRUD、来源执行开关和手动运行、来源健康、池与目标质量查询、批量取代理、使用反馈。管理前端调用这些业务接口，节点、日志和平台任务详情直接链接 Crawlab。

不保留上一版 /internal/attempts、通用任务输入／回执服务等端点作为既定范围。新增接口只有明确业务需要时才定义，HTTP 命名和返回模型在框架联调后定稿；旧调用方兼容另行核对。
