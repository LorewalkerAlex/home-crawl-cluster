## 有限反馈重传与去重（2026-10-29，用户确认）

用户接受低开销的有限重传＋结果去重。每次实际访问由执行侧生成result_id，无需向M05预登记使用身份；同一次反馈的网络重传保留原ID和原内容，不重新访问代理。结果先在发送端内存保留，暂时失败按可配置次数／等待上限退避重传；进程退出或超过上限可以丢弃，不新增持久发送队列或常驻服务。此确认没有恢复原先批次／成员分发凭证方案，不给每次获取代理增加数据库写入。

用户随后明确去重只放短期内存，撤回SQLite唯一凭证／feedback_receipts表。等待处理和近期已处理ID在M05内存中保存，同ID重传共用原结果或返回已处理；首次质量事务成功提交后才标为成功，重复不再次计分／刷新时间。真正再次访问使用新ID；服务重启和窗口外可能重复计分按个人场景接受，不增加持久防御。

内存ID记录在已有短期重传等待窗口内有界保留并到期移除；执行侧超过窗口不再自动重传。用户随后要求简化，已撤回completed_at及反馈接收期限；不按执行侧访问时间拒绝旧反馈。接受去重记录清理后极晚旧结果可能再次计分，不为此增加规则。下文较早的observed_at接受期／feedback_until属于旧建议，不作为统一反馈入口的当前要求。去重只查询内存，不增加数据库读写；正常情况额外生成ID及保存短期内存记录，网络重传只在异常时发生；没有新增吞吐实测，不把开销小描述成性能保证。

具体统一JSON、接口路径及HTTP提交确认继续作为下一步协议建议；不再增加反馈时间校验；本次只记录已确认取舍，不改PoC源码、迁移或部署。较早的分发批次持久登记、usage_id／check_id作为反馈前置绑定，以及按来源分开的处理路径均不自动成为新统一协议要求。

## 两个时间决定自测与统一反馈（2026-10-29，用户修订确认）

用户撤回独立测试中／可测试状态和必须由匹配check_id释放占用的设计。每个代理＋目标／当前revision仅以两个调度时间表达选测依据：last_feedback_at为M05最近处理并成功提交有效新反馈的时间；last_test_scheduled_at为最近成功发布自测小批的安排时间，由M05在发布后保存。字段名为推荐命名，不表示schema已迁移。测试状态不再单独持久维护，也不需要反馈释放或超时清状态。

配置min_test_interval为新反馈后的最小复测间隔，test_timeout为一次安排后无新反馈时最多等待的期限。初始两个时间为空。选测解释如下：

```text
反馈已到期 = last_feedback_at为空
             或 now - last_feedback_at >= min_test_interval

无需继续等本轮 = last_test_scheduled_at为空
                 或（last_feedback_at不为空 且 last_feedback_at >= last_test_scheduled_at）
                 或 now - last_test_scheduled_at >= test_timeout

可安排自测 = 反馈已到期 且 无需继续等本轮
```

即：安排后已有任何有效新反馈，按这次反馈的最小间隔判断；安排后仍无反馈，等到test_timeout再允许选择。timeout只解除等待限制，不绕过仍未到期的最新反馈间隔。两种时间均由M05以一致时钟记录，用处理／提交顺序解释，不依赖Worker机器时钟或按请求发生时间重新排序；实际持久时间精度与同事务排序在实现时确保一致。用户随后明确当前发布端按单实例、逐网址／同网址轮次不重叠执行，不设计并发领取。M04可读取当前目标下全池的轻量汇总字段，按双时间规则判断后切块发布；不一次载入全部网址或历史明细。发布每个小批成功后，再由M05批量更新该批成员的last_test_scheduled_at；推荐逐批更新，不必等所有批次发布完。明确发布失败不更新时间。用户接受此简单方向：若平台已接收而更新时间前程序中断，下一轮可能重复安排，不为消除此窗口增加原子领取／占用协议。该重复是可接受的恢复取舍，不是严格只执行一次保证。时间应表示该批被安排的时刻；数据库实际延后提交不应伪造一次更晚的新安排。原子领取及多发布实例防重要求撤回，不据此改动已确认的获取缓存并发处理。

自测及实际使用走同一反馈业务协议和处理链：验证身份／目标、去重、更新二元历史／分数，成功时更新耗时EWMA，刷新last_feedback_at并一起提交。反馈不修改last_test_scheduled_at；重复、无效、未发生访问的本地异常／取消不刷新有效反馈时间。check_id／task_id若保留，只用于关联、去重或任务观察，不再作为改变组合选测资格的释放凭据；反馈不必知道当前安排的测试身份。具体统一JSON字段、认证和有界去重策略仍待确认，之前分发批次／usage_id接口草案并未因此自动采纳。

没有反馈不伪造失败，不更新时间；无需每组合定时执行释放操作，下次查询比较时间即可。任何新的有效反馈可以让组合从最近反馈重新计时，原Crawlab任务不会被自动取消；本方案接受实际任务仍可能重叠，不承诺严格单任务互斥。代理获取继续只按目标分数及已确认缓存规则，不按这两个时间过滤。使用反馈并不更新“安排自测时间”，普通获取代理也不更新这两个时间。

资源方面只维护两个调度时间，有限查询及批量提交复用M05 SQLite单写入口，不增加状态库、Redis、任务逐个对账或清标记服务。时间差／OR条件的索引及查询计划待实现验证，不承诺必然索引命中或已测吞吐。原PoC代码仍保留active_check_id等旧字段，尚未改代码、迁移数据库或部署服务。当前单实例串行发布、发布后保存安排时间的规则覆盖下文较早“先占用再发布／原子领取”的建议，后者不作为当前实现前提。下文旧二态／释放占用／迟到反馈不得释放新占用的文字均为已被本节替代的历史设计；任务本身完成与业务批次统计是另一个层次，不由两个调度时间证明。

## 代理获取的有限候选队列（2026-10-29，用户确认）

用户接受按需拉取、小批缓存、固定有效期和内存弹出。按测试目标＋当前配置revision分别维护队列及拉取时间，初始为空且未拉取；批大小和有效期配置化，100仅为批大小示例。每次请求先判断队列是否为空；为空则拉取，否则检查自上次拉取是否已过期，过期也重新拉取。数据库选取该目标有评分且达到配置最低分的候选，按稳定性分数降序、同分成功耗时EWMA较低优先截取有限批次，在内存打乱并替换整个旧队列，再弹出头部一个。自测占用不排除获取；未评分组合先自测。

使用deque.popleft等常数时间弹出方式。每目标缓存以进程内异步锁合并并发补充，进入锁后复核条件，保证同进程并发请求不重复装载／弹出；不同目标不共用全局锁。锁只保护业务缓存操作，不以SQLite写事务包住等待。成功拉取后用单调时钟记录装载时间，每次获取不延长有效期；拉取后仍为空直接返回暂无可用代理，不在单个请求内反复查询。查询失败不标记装载成功，不将过期旧队列当作新结果；具体HTTP错误格式待接口细化。

本方案明确接受缓存有效期内的评分滞后，不要求每次弹出都查数据库。只读有限质量汇总，不现场扫描历史样本、不做数据库全表随机排序；每目标缓存及缓存目标总量均设上限。若批次在过期前用完，读取可按批摊薄；低频调用可能由有效期触发刷新，不能将每100请求一次查询当作保证。索引／峰值负载尚未实测；不新增Redis。空结果短缓存仅是今后出现高频空池请求时的可选优化，本轮不要求实现。

本次确认设计，未改业务代码／schema或部署服务。当前约束按单业务进程内存缓存解释；多进程共享和全局不重复分配未在本次确认范围。使用结果回传的身份、去重、期限及返回字段接下来讨论。

## 成功耗时指标（2026-10-28，用户确认）

每个代理＋测试目标／当前配置revision保存一个成功耗时EWMA值，alpha配置化，E_new=(1-alpha)*E_old+alpha*本次耗时。第一次有效成功耗时直接初始化，无该类数据时为NULL；失败只进入稳定性评价，不把超时上限伪造成成功耗时，重复／无效反馈不重复更新。单次latency_ms仍由回传提供，但无需为速度指标保存50条原始耗时。

按M05已确认的反馈处理顺序平滑；合批包含同组合多个有效成功结果时按顺序合入，然后与位图／数量／评分一起在原事务提交，不把批内简单平均当作等价EWMA，不增加单独写事务或常驻服务。取得代理时稳定性优先，同分再参考较低耗时，跨网站淘汰总分不加入耗时权重。该指标是平滑趋势，不是精确最近50次中位数或下一次耗时保证。

正式推荐字段使用successful_latency_ewma_ms；原PoC中的latency_median_ms继续按原实现解释，本次不修改应用代码／schema、不启动迁移或部署。

## 抓取轮前容量清理（2026-10-28，用户确认的范围）

用户补充条件后选择：M03每轮发布抓取前调用M05检查池数量；只处理轮前已经超过配置阈值的部分。满足条件的末尾候选清理完才发布本轮来源任务，此处旧等待条件已被2026-10-29用户修订：后续按固定周期再次发布，不等待本批抓取或回传结束。用户允许本轮抓取再次超量，不为了这个池数量规则增加单轮新增预算、抓取中清理或入库硬挡板。

清理增加可配置的最低已测试次数；未达门槛的新代理不进入此次末尾淘汰候选。方向仍是按跨目标的总分从低到高处理轮前超量部分，不把单目标失败视为全局失效。用户进一步澄清：最低测试次数就是可配置门槛，配置为50也可以，不再反复要求其选择具体值／计数实现。对象是单个代理，不是来源网页或抓取次数；无需每个网址各达门槛。50是配置示例，不绑定位图长度；M05按业务语义及读写成本选择计数实现，不能因窗口封顶让合法门槛永久不可达，也不能为局部性能改变保护含义。总分的具体汇总字段／同分规则及正式单目标算法仍待细化。

用户接受清理期间测试／调用反馈引起的末尾分数变化，不冻结全部评分，也不追求持续重排。选定候选后按M05单写／短事务及既有引用条件执行即可；不因为分数小幅改变不断重试，但不因此跳过身份、去重或事务规则。来源少且有timeout，整轮等待是用户认可的取舍；任务总超时及业务收尾仍需实现明确结算，不能仅以单次HTTP超时替代整个来源任务的结束判断。

轮前数量记为N，阈值为L，需要删除的数量为max(0,N-L)。本轮新增不追加进这个删除额度；没有超量时直接进入抓取发布。阈值不是整轮持续硬上限，库文件／磁盘等现有物理容量错误仍正常报错，不据此新增另一套池数量挡板。

候选不足边界：用户认为实际不太可能发生，并认可先按候选充足的正常路径设计，不建立专门的补测等待／延期调度机制。实现保留最低次数条件及清理结果检查，真有不足则记录实际情况再处理；不为了凑删除数绕过门槛，也不擅自定义仍超量时正常发布。此前“先等M04补测再抓取”不作为默认方案。来源轮次结束／超时后的迟到回传及在途引用仍按后续具体设计细化。最低次数统计口径的建议见存储稿，尚待用户确认，本轮不修改应用或服务器。

## 二元历史的顺序（2026-10-28，用户确认）

用户认为乱序回传对该评分历史影响不大，接受接收顺序或另一种固定顺序。首版统一定义为：M05单写入口实际处理并成功提交有效反馈的先后；同一写入批次内按输入列表顺序，跨批按单写入口顺序，不依赖毫秒时间戳打破并发平局，也不按Worker请求发生时间重新插入或排序。

同一事实先按既有身份去重：重复回传不追加、不移位；无效反馈不进入序列；事务失败时位图／长度／评分一起回滚，后续首次成功提交才进入一次历史。合批需保留每个代理＋目标组合的有效反馈处理顺序，可在应用内连续更新后一次落库，不因只写一次而丢失中间结果。

本决定仅确定候选二元历史的排序语义，不表示时间字段全部取消，也不改变既有最近真实反馈时间、迟到有效性／测试身份检查或去重规则。Worker测试时间可在确有诊断／时效用途时保留，但不参与位图排序。逐条过期、位图正式实现和schema迁移仍未确定／实施；速度设计已按上方确认EWMA，但未修改原PoC；当前PoC源码的observed时间排序尚未因此修改。

### 1. 通道及最小身份

建议 Worker 通过镜像配套 SDK 输出结果，M05 经原生 GET /api/tasks/{id}/data 读取，统一进入其 SQLite 写入口。程序仍由Crawlab分发运行，不新增领取器、事件平台或Redis；Worker可以读取本轮配置／测试清单，但不再为开始、每条结果、结束各建一套业务写回调。前端读取平台执行状态与业务入库状态。

同一测试URL的一批代理仍是一个Crawlab任务；例如100个代理产生100条测试结果，不是启动100个进程。来源分页也由一次网站程序处理。每条结果为一个小JSON对象，避免一次把整站代理列表或正文塞入一个巨大JSON。网站脚本只负责请求／解析并交出端点，公共适配补身份和运行统计；Scrapy使用标准Item Pipeline和生命周期扩展点，不自行重建下载框架。

| 公共字段 | 建议含义 |
| --- | --- |
| schema_version | 结果结构版本，首版1；与目标测试规则revision分别使用 |
| kind | proxy、source_page、check_result、run_summary |
| record_no | 本次执行内从1递增的记录号，覆盖所有结果类型，重传不改变 |
| run_marker | 公共入口启动时生成一次随机标识，所有记录相同，复用smoke已演示的模式；用于发现同一平台任务混入多个执行的结果，不另建通用执行服务 |

原生task_id及结果_id由平台上下文取得，不要求每条复制。来源身份、目标ID／revision、网络范围由已经核验的本轮来源配置或测试清单提供，不信任结果自行改归属。同一task出现多个run_marker或相同记录身份内容冲突时停止最终确认，保留排查；不自动混合。平台同ID重派及SDK异常重试行为尚未验证，首版不承诺自动恢复同ID多进程执行。主动重新测试建立新小任务及新成员身份，不用旧member_id表示一次新网络访问。

### 2. 来源抓取输出

代理记录只保留端点，示例：

```json
{"schema_version":1,"kind":"proxy","run_marker":"00000000000040008000000000000001","record_no":1,"host":"192.0.2.10","port":8080,"scheme":"http"}
```

host是代理地址，port为整数，scheme指连接代理的协议，不代表目标网站的HTTP／HTTPS协议。192.0.2.10仅为文档地址，不能当作有效公开代理。协议支持范围另随执行环境确定，不能凭字段宣称已支持所有SOCKS等协议。

此记录不含source_id、页面URL、发现时间、抓取时间、分数或业务proxy_id。业务代理表不保存来源映射；首次／最近发现时间仍留M05字段讨论，不因接口先行引入。临时record_no／run_marker用于传输校验，不进入代理资料。

独立页面记录source_page建议包含page_id、page_url、outcome、http_status、error_code、parsed_count。page_id在发起逻辑页面请求前固定，重试不换；同URL的独立抽样可有不同ID。每个逻辑页面输出一个最终结果。page_url不含凭据／私密查询参数；error_code使用有限枚举，不保存正文和完整堆栈。outcome区分response、request_error、parse_error、execution_error；parsed_count为本页解析出的候选数，不承诺等于去重后新增代理数。页面记录不附代理清单。

来源身份只保存在本轮上下文和独立健康统计。正常请求结束但候选为零，显示零产出；不能推断解析器一定坏，也不能显示有代理的健康成功。动态分页的结束规则由该网站脚本定义，结果序号和摘要只能证明声明产出完整，不能证明网站所有真实内容都已抓到。

### 3. 测试任务输出

M04发布前固定小任务成员：member_id、proxy_id及端点、target_id、target_revision、请求URL／超时等快照。每个member代表本轮的一次网络尝试，M05按清单核对结果，不单凭条数接受。测试记录示例：

```json
{"schema_version":1,"kind":"check_result","run_marker":"00000000000040008000000000000002","record_no":1,"member_id":"member-example-001","observed_at":"2026-10-25T08:00:00.000Z","outcome":"response","http_status":200,"latency_ms":420,"error_code":null}
```

| 字段 | 必要性及规则 |
| --- | --- |
| member_id | 映射固定成员及目标快照，不能换成任务外代理或重复占用同一成员 |
| observed_at | 实际尝试开始时间（UTC）；用于近期评价和少测规则，不能用导入时间替代；合法性和时钟误差仍按M05规则核验 |
| outcome | response、proxy_error、execution_error、cancelled |
| http_status | 有HTTP响应时必填；其他情形null |
| latency_ms | response从尝试开始到响应头的耗时；无响应首版可null，不把失败耗时放入成功速度统计 |
| error_code | 失败时使用有界类型，如connect_timeout；不上传异常全文 |

Worker不输出success或score。M05由固定规则派生：response且200为成功，其他HTTP响应或已确认代理访问错误为失败；执行环境错误／取消不评分。无法合理归因给代理的基础设施故障不硬算代理失败，错误分类需随实际aiohttp异常验证。未收到结果也不合成proxy_error。

全部100个代理都超时可以是100个已处理成员和一次完整测试运行；代理质量降低，但不意味着测试程序或结果导入失败。若只收到80个成员，已收到的合法观测可以处理，另外20个保持缺失／未完成。配置revision已变或目标已删除时，记录处理原因，不将旧结果计入当前质量，也不重建已删目标；其他目标成绩不受影响。

### 4. 结束摘要及完整性

两类任务正常收尾都输出一条run_summary。以来源任务输出200条proxy、2条source_page为例：

```json
{"schema_version":1,"kind":"run_summary","run_marker":"00000000000040008000000000000001","record_no":203,"close_reason":"normal","counts":{"proxy":200,"source_page":2,"check_result":0}}
```

counts只统计本轮应输出的数据记录，不含摘要自己；不是SQLite新增行数。公共发送器在生成数据记录时固定编号及计数，先排空数据输出，再生成最后一条摘要；重传沿用原记录。异步SDK调用返回不能当作全部数据已持久化，必须靠M05读取核验。进程崩溃可能没有摘要，不保证任意错误都能执行finally／关闭回调。

对声明N条数据的正常完整任务，须有且仅有一份逻辑结束摘要，数据record_no恰好覆盖1..N，摘要编号N+1，分类型计数一致，所有记录属于同一run_marker。重复传输记录按身份折叠，相同身份不同内容报冲突。测试还须逐成员匹配固定清单：100条结果若缺一个成员却重复另一个，仍不完整。未知字段版本、非法端点或非法测试记录不能静默丢弃后将该轮算完整。

源summary.close_reason建议使用normal、partial、failed、cancelled、skipped、limit_reached等有限值；它是执行端声明，不是Worker授予业务成功。normal但零代理单独显示zero_output；达到配置抓取上限明确limit_reached，不能冒充抓完。测试代理的访问失败写逐项结果，不能据此把close_reason改成程序failed。

### 5. M05导入及状态规则

首版建议优先处理平台已进入终态的有限任务；平台running／pending仍直接展示Crawlab状态，不持续镜像每个阶段。0.6.3源码按结果_id倒序、skip／limit分页，写入中移动的页不能作可靠游标；任务结束后也不能假定结果立刻稳定，可能有SDK／平台写入延迟。

M05轮询只选登记程序及允许处理窗口内的任务，分页读取、锁外校验，逐批通过统一写入口处理。每条导入凭证至少含task_id、run_marker、record_no及规范内容摘要；凭证、业务变更与处理计数在同一短SQLite事务提交。测试另按member_id的业务身份避免重复评分，质量汇总只重算本批影响的组合。代理端点使用唯一键UPSERT，不逐条先查再插，不把跨网站发现去重误作结果缺失。

进程在提交后、保存内存页号前崩溃，可以重新分页读取，由已提交凭证阻止重复影响。首版不把page=3或“已读到最后”作为唯一持久进度，也不要求一次把全部任务装入内存。读取期间total变化、编号缺口或摘要缺失时，在有限退避和截止时间内重扫、仅处理新增身份。完整集合确认后，以同库事务提交最终业务状态；容量／提交错误不能先报成功。到期仍缺结果标记不完整，保留合法已提交部分，不永久保持运行，不把缺失项计为代理失败。

| 平台／结果情况 | 建议业务呈现 |
| --- | --- |
| running | 执行中，暂不作最终完整性判断 |
| finished，摘要／成员未齐 | 等待结果；到期后结果不完整 |
| finished，合法结果齐备，最后事务已提交 | 导入完成；抓取健康或代理成功率另算 |
| error／cancelled，有合法结果 | 可导入合法部分，显示执行异常／取消及部分已保存，不显示整轮成功 |
| 读取、校验或SQLite提交失败 | 显示对应导入错误／待重试；不篡改平台状态 |

大测试批次是否结束，应以其固定小任务清单逐一进入业务终态为准，不只数Crawlab的finished。缺失任务达到期限也须以明确不完整／取消结算，才能区分批次“结束”和“全部完成”；父批次允许有限重叠／等待策略仍留M04审阅。

凭证仅保留有限处理／重试窗口；清理后不承诺旧数据永久幂等。旧任务不能因凭证清理再次当成全新结果导入：只接收已登记且在固定允许处理期限内的运行，到期后关闭导入资格。新网络测试建立新成员，不将重复读取原观测视为新测试。

### 6. 资源与实现验证边界

- 首版可考虑100个代理／测试任务、200条／查询页、1个活动导入任务，全部为可配置候选值，不是实测容量。源任务另设页面数、结果条数及运行时间上限；触顶明确结束原因。
- 内存只持有限查询页、待写队列及当前有限校验状态；JSON字节、队列条数／字节、活动导入数均设上限。原生API的size是条数，不等于字节上限，实际大响应的限制及异常处理要验证。
- 合批按数量／字节／最大等待触发，首项起计且不不断延后；任务最终确认及时flush。平台HTTP、JSON规范化、等待不放进SQLite写事务。高频调用使用已维护质量，不在此讨论额外排名服务。
- M05多了短期导入凭证、运行统计及成员状态写入，需纳入总容量与I/O预算；结果通常先写MongoDB再写SQLite，这是可靠中转的明确空间／写入成本，并非无额外开销。
- 平台原生结果／任务／日志和业务记录分别有条数、字节、保留期限及满额处理。正常入库后才能进入安全清理范围；M05故障时不能无限积压，也不能静默删除未导入数据。应限制新增任务、提示容量，并对最终过期数据明确记录结果丢失；与原生Schedule／入口开关的协作及清理API尚待验证，不声称已建立硬磁盘上限。
- 当前只提出文档建议。后续本地隔离验证应覆盖重复读取、同ID内容冲突、缺摘要／缺成员、分页变化／迟到写入、提交前后中断、目标revision变化及小批写入；平台同ID重派、SDK错误及有限清理另按实际版本验证，不重跑已通过的三条smoke作为这些能力的替代。

当前数据链路未定稿。根据用户要求重新评估后，助手优先建议验证同目标小批执行、逐项结果／摘要经配套 SDK 写平台原生结果，再由 M05 有界导入；直接业务 HTTP 回传保留为备选，不同时实施两套默认链路。字段、原生接口及完整性核对按当前 0.6.3 验证，详见方法设计；下文 HTTP 三动作和测试回调路径不是已经确认的要求。

字段定稿边界：代理长期保存什么由 M05 审阅；M03 只约定必要执行输入、提取输出与独立运行统计。用户已确认去掉代理来源，尚未确认 proxy.fetched_at 或全局发现时间；下文相关时间与校验保留为候选协议，待 M05 确认字段用途后统一修订，不表示已实现或必须保存。网络消息带有上下文字段也不自动意味着业务库必须逐项落盘。

- 业务 API 前缀 /v1；Worker 受控输入／反馈的前缀 /internal/v1。HTTPS + Authorization: Bearer；令牌从私密配置提供，不进入 URL、命令行或公开文件。
- 使用现成 HTTP／JSON 和 Crawlab 原生结果，不增加消息中间件。来源仍是标准 Scrapy Spider，不定义新的插件包协议。
- JSON 使用 UTF-8，Content-Type: application/json。对象中的未知字段拒绝，缺少可选字段等同 null。JSON 数字不接受 NaN／Infinity。
- HTTP 时间为 RFC3339 UTC，固定毫秒及 Z，例如 2026-10-24T08:00:00.000Z。服务端 received_at 为准记录到达，observed_at 为客户端记录的尝试开始时间；耗时使用单调时钟。代理资料的 fetched_at 为页面成功取得响应的时间。
- 本协议生成的批次／成员／请求／使用 ID 用 UUID 字符串；source_id、target_id 用显式登记的稳定标识；Crawlab task_id 为平台原生不透明字符串。record_id 为不超过 160 个 ASCII 字符的稳定业务键，不是新增通用任务 ID。
- 同 ID 同规范化业务内容重传等同重复；同 ID 不同内容返回冲突。摘要使用标准 SHA-256，忽略 JSON 字段顺序和服务端生成字段，保留业务字段含义；不是用 JSON 原始字节比较。
- 修改接口提交数据库事务后才返回 200／201；不提供先返回 202 再放内存的写入确认。锁超时／临时故障返回 503，可用同 ID 重试。每包最多 500 条、HTTP 正文最多 1MiB，超过拒绝；分页 size 默认 100、上限 500。
- 新观测发生时间不能晚于接收时间 60s，也不能早于接收时间 24h；未过批次凭证保留期的同内容记录可返回 duplicate。超出接收期返回 OBSERVATION_TOO_OLD，不把迟到当失败。发生时间、延迟与时钟异常分别保留，不静默修改时间。
- 对允许的客户端时钟超前，服务首次接收时明确派生 effective_at=min(observed_at,received_at)，保留原始 observed_at／received_at，窗口与排序使用 effective_at；重复上传不重算该值。客户端不能提交 effective_at。
- 用户认可缓存合批，具体候选在 [SQLite 流程](../../apps/proxypool/storage.md)：M05 有界队列／统一写入入口可按条数、字节和最大等待合并小包；生产者也可小包发送，但两端共用等待预算。原 100 条／1s 仍是未确认示例。单个 HTTP 包保持原子语义，合并包只有最外层事务提交后才分别 ACK；不把 received 或 queued 当 committed。有限样本／短期凭证规则仍按存储草案，未因本轮全部定稿。
- 上述 1MiB／500 条是 M05 HTTP 包上限。若经过研究中的 Crawlab Python SDK stdout IPC，另受编码后整行≤32KiB、≤100 条或≤1s 的候选适配限制，需按实际编码字节拆批，不能把 HTTP 大包直接写为一行；锁定版本后复核读取器上限。
- 初始入口预算为净新增观测 5 条/s、测试与分发合计新批次 1 个/s、新成员 10 个/s，分别允许有限突发；具体桶量见存储方案。超出短期限流返回 429 和 Retry-After；达到存储硬容量返回 503 CAPACITY_LIMIT。重复既有业务身份不重复消耗存储配额，仍计入实际服务处理负载。

令牌只映射个人程序身份与权限：admin 管来源和目标；caller 取代理与反馈；worker 读取允许输入，当前 M03 候选允许提交已核验来源运行的开始、结果和收尾，不允许直接设置业务成功或分数。业务内 importer 在平台中转方案中自行读取 Crawlab；直接反馈方案使用受控写入口，不向所有 Worker 暴露任意 observation 修改。producer_id、caller_id、origin 和 success 由服务端确定，客户端不得伪造。

源和目标普通 CRUD 由标准 API 校验实现，不创建新的通用配置服务。source 的入口只能引用已经审查、登记和同步的代码。源配置保存响应包含 desired_enabled、sync_status（pending／synced／error）、schedule_id 和可脱敏错误，不能把本地保存成功显示为 Crawlab 已启用成功。平台调用不能放在 SQLite 写事务中。

source PUT 的业务字段固定为 name、homepage_url、entry_id、enabled、cron、params；source_id 取路径，revision、schedule_id 与 sync_status 由服务端生成。cron 按选定 Crawlab 版本支持的分钟级表达式校验；params 必须匹配登记入口的允许参数，不能含执行命令或任意文件路径。PATCH 首版只接受 enabled；DELETE 为幂等归档。source 修订同样用 If-Match／If-None-Match 控制覆盖。

target PUT 的业务字段为 name、enabled、url、method、success_status、timeout_ms、follow_redirects、verify_tls、network_scope、headers_ref；其含义与下文快照一致。timeout_ms 取 1000—60000 整数，默认 10000；保留不支持的能力用明确 422，不静默忽略。首次 revision=1；显示名称或开关变化也产生配置 ETag，但只在测试语义变化时增加测试 revision，两个标识分别返回。If-Match 引用资源 ETag，避免单凭测试 revision 覆盖并发名称／开关修改。

新增网站产生新的 target_id 和 revision=1 配置行，不对代理表增加网站列。修改测试语义增加 revision、清理旧质量并重新预热；旧批次仍按当时快照校验，合法反馈只作 obsolete_target 确认。PATCH enabled=false 仅停用，当前 revision 的已有批次反馈仍正常处理；DELETE 后不再建立该网站质量。重新添加同 URL 使用新 target_id。目标、版本、质量组合及批次的数量配额统一见存储方案，超额明确报错。

列表 cursor 是应用查询约定，不承诺 Crawlab 支持相同分页；平台实际 page／size 只由适配器处理。源健康的页面列表也分页，不一次返回全部历史。health 响应至少含 source_id、enabled、latest_task_id、latest_run_outcome、last_successful_crawl_at、page_counts、valid_proxy_count、import_status、pages_cursor 和 platform_task_url；每个页面包含其最终响应／解析结果。节点异常单独为 execution_error，零产出明确为 zero_output，不能折算为来源网站的 0 分或健康成功；不在首版另造来源百分制分数。

## 目标配置与成功定义

目标请求快照示例：

```json
{
  "target_id": "site-example",
  "revision": 1,
  "url": "https://example.invalid/check",
  "method": "GET",
  "success_status": 200,
  "timeout_ms": 10000,
  "follow_redirects": false,
  "verify_tls": true,
  "network_scope": "personal",
  "headers_ref": null
}
```

revision 为服务端递增整数。首版只允许 GET、200、禁止自动重定向、开启 TLS 校验；不提供可随意上传的成功判定代码。headers_ref 默认为 null；将来确需请求身份时只引用服务器私密配置，真实 Cookie 等不放在公开示例和任务命令行。

首版 headers_ref 仅允许 null；非空明确返回 UNSUPPORTED_REQUEST_IDENTITY，待有具体身份需求再实现安全传递，不能把尚不存在的凭据管理当已提供能力。network_scope 可从管理员预设列表选择，默认 personal；新网络范围的令牌／节点归属由部署配置指定，不自动相信请求自报。

测试固定 url。调用方可访问同一 origin 下其他 GET 路径，但要遵守相同请求语义并回传实际 request_url；这只是代表该网站的访问证据，不证明所有路径都可达。若登录态、请求方式、路径规则或网络范围差异导致表现不可比较，应登记不同目标配置，不混入同一统计。request_url 不得带用户信息、凭据或敏感查询参数；在执行前约定可公开记录的 URL，不能靠日志泄露请求身份。

success 是服务端派生字段：outcome=response 且 http_status=200 时 true；其他 response 或 proxy_error 时 false；execution_error／cancelled 时 null。取得响应头即完成这一评价，latency_ms 从连接尝试开始到响应头到达。正文解析失败不反向修改已经成立的 200；若要测试正文，另立新规则再演进协议。

## 来源输入与输出

以下来源示例及“三动作”是先前候选，保留用于对照，不与本文2026-10-25分析稿同时作为当前默认。旧fetched_at及直接回调等字段没有因此获批；本轮优先建议不加入发现时间且复用原生结果，业务方案仍待审阅，代理持久字段仍留M05。

来源执行沿用 Crawlab 的固定登记命令和参数；只传 source_id、revision 等小参数。Worker 的配置读取请求需要认证，并由服务核验 task_id 的平台程序／周期归属；定时任务可以在第一次读取输入时据平台元数据登记运行，不相信任意客户端自报的来源。

Worker 启动前复查开关和 revision。来源停用或配置已经过期则跳过新抓取，不能记为网站故障；已经开始的运行按其快照接收结果。代码经审阅再同步，不因为文件符合 JSON 字段或放入目录就得到执行授权。

代理 Item 使用配套 Pipeline 向 Crawlab 结果通道输出；网站身份只在本次运行上下文及独立统计中使用，不重复写入代理 Item：

```json
{
  "schema_version": 1,
  "kind": "proxy",
  "record_id": "proxy-000001",
  "host": "192.0.2.10",
  "port": 8080,
  "scheme": "http",
  "fetched_at": "2026-10-24T07:59:00.000Z"
}
```

192.0.2.10 为文档专用示例，生产公开端点校验不接受它。http 是代理接入协议，不等于目标只可 HTTP。host 规范化，IPv6 的 URI 表达加方括号，port 为整数。来源侧不知道业务 proxy_id，由服务端按自然键创建／查询。

proxy.record_id 在同 task 内唯一并在重传中不变，由薄适配在生成时分配无网站／页面／端点含义的序号或随机标识，不拼入地址。同一次页面内重复代理合并为一个 Item，不同页面发现同端点可以各有 Item，业务代理仍合并为一行；页统计单独计数，不将两者建立持久映射。source_page.page_id 在发起该逻辑页面请求前固定，重试不换 ID；同 URL 多次抽样属于不同 page_id。重传重复已经生成的事实及其 ID，不重新执行抓取后冒充原记录，也不重新生成 fetched_at。

fetched_at／页面时间必须位于经核验运行的开始结束范围内，允许 60s 节点时钟误差；未结束任务只允许截至当前服务时间加误差。不能用任意未来日期刷新全局 last_seen。网站代码只提供自己提取的端点字段；schema_version、record_id、时间和独立统计的来源／页面字段由项目薄适配补齐，不要求每个 AI 编写的网站 parse 重写整套协议。代理入库只更新端点和全局发现时间，不保存当前 source_id 或 task_id。

另外两类结果共用 schema_version=1 和 record_id：

| kind | 必填业务字段 |
| --- | --- |
| source_page | source_id、source_revision、page_id、url、started_at、finished_at、outcome、http_status、error_code、retry_count、extracted_count、valid_count |
| run_summary | source_id、source_revision、started_at、finished_at、close_reason、expected_proxy_records、expected_page_records、stats |

source_page.outcome 为 response／request_error／parse_error／execution_error。正常收到 200 但未提取到代理，标为 response 且 valid_count=0，前端显示零产出；不能当作健康成功有代理，也不凭零产出断定解析器损坏。部分页面失败与其他页面成功并存。source_page 和 run_summary 不含代理地址清单，stats 只使用选定的脱敏请求、响应、重试、丢弃和异常计数，不上传任意对象或全部内存状态。

expected_* 统计实际应输出的去重业务记录数，不是页面中全部文本匹配数。普通 print 是日志，JSONL 也不会自动保存为 Crawlab 结果；必须通过已经验证配套的结果通道。

## M03 三个反馈动作：本轮具体建议

2026-10-24 用户要求具体说明开始、提交、结束如何处理。以下只针对一轮来源网站抓取，是待审阅接口建议，不代表已确认或实现；Crawlab 保留代码分发／执行，业务成功由 M05 的数据库提交确定。使用现成 HTTP、Scrapy Pipeline／生命周期与 SQLite 事务，不新增通用任务平台。

### 共同身份和范围

平台注入的 CRAWLAB_TASK_ID 对应路径 task_id，每次新发布／重跑使用新的平台 task_id，本轮分页共用该身份，不每页生成一个平台任务。建议执行程序启动时另生成一次 execution_id，start／batches／finish 都携带它；HTTP 重传不换 ID，服务在该 task_id 首次开始时原子绑定，防同一平台 ID 被重新分配后由两个进程混传结果。这是一次执行会话的绑定，不另建通用 attempt／租约服务。服务用认证身份和平台程序／参数核验来源、修订及允许入口，不能信任客户端随意声明。平台查询在写事务外进行，验证后保留本轮必要上下文，不每包重复查询 Master。

来源身份只在本轮执行及页面统计里使用，不写入代理行。每轮按 task_id 独立保存，旧任务收尾不会修改另一 task_id 的新任务状态；不在来源配置中用一个可反复覆盖的 running 值代表全部运行。若平台任务 ID 关联返回晚于 Worker start，幂等补齐同一行，不将已开始的状态降回排队。

### 1. 开始：POST /internal/v1/source-runs/{task_id}/start

请求提供 source_id、revision、execution_id。服务核验执行范围、来源开关、配置与代码入口；允许执行时，经统一写入口及时提交本轮开始记录、执行会话、首次开始时间及有限截止时间，返回 committed=true、proceed=true 和不可变配置／允许限额。Worker 取得确认后才发起网站请求。停用／过期配置按明确原因跳过，不记为网站访问失败；已运行任务是否立即取消仍按独立控制操作决定。

同 task_id、同来源修订且同 execution_id 重复 start 返回原确认，不重置首次开始时间或无限延长截止；不同来源／修订冲突，不同 execution_id 返回 RUN_ALREADY_STARTED，不给另一个进程重开同轮。已结束运行重复 start 返回终态并拒绝重新抓取。全新重试通过 Crawlab 新 task_id 发起，不把旧运行重新置为未完成；平台同 ID 自动重派不等于业务已支持断点续跑，恢复入口和拒绝后的新发布需随所选版本验证。来源重叠控制仍是独立待确认策略，不在此暗加整站排他锁。

### 2. 分批：POST /internal/v1/source-runs/{task_id}/batches

请求含 execution_id、batch_no（从 1 递增）、records。records 可包含标准代理端点和独立 source_page 统计，不附逐代理来源字段；完整代理字段留 M05，本节只定反馈封装。每轮先采用一个发送器按顺序提交，收到当前包确认后再提交下一包；网站请求／解析仍可并发，缓冲必须有界并定时 flush，不能为等满批而永久阻塞。

服务在事务外规范化和计算包摘要，事务内核对本轮有效性／期限、包号、数据约束及配额。将业务数据、独立页面统计、包号／摘要凭证、分类型计数及本轮进度一并提交，最外层 COMMIT 后才返回 committed=true、duplicate=false、next_batch_no。包内有错误按已约定全包原子语义拒绝；多个请求合并提交仍按 SQLite 流程保留各包原子性。

| 情况 | 服务行为 |
| --- | --- |
| 相同 task_id＋batch_no、相同规范内容重传 | 返回 duplicate=true 和原包已提交确认，不重复累计数量或改变质量 |
| 相同包号但内容不同 | 409 BATCH_CONFLICT，不覆盖旧数据 |
| 尚未提交前序包就提交后序包 | 409 BATCH_GAP，返回 expected_batch_no；不标本轮成功 |
| 任务已关闭／失效 | 拒绝新包，已提交包的同内容重传仅按保留期返回原确认 |
| 队列满、提交失败或临时不可用 | 明确可重试错误，不返回已入库；Worker 保留原包号和内容 |

记录计数是已提交的有效传输记录数，不是本库新增代理数或全局唯一 IP 数；同端点已经存在仍可作为本包记录合并。批次凭证只存任务、包号、摘要、计数和有限确认，不附代理清单／端点明文。HTTP 超时不证明写入未发生，必须用原包重传；Worker 重启后不能用新抓内容冒充同一个旧包。

### 3. 收尾：POST /internal/v1/source-runs/{task_id}/finish

Worker 在 Scrapy 请求／解析结束、所有输出包均收到提交确认后请求收尾，提交 execution_id、last_batch_no、record_counts（按 proxy／source_page 分类）、close_reason 及有界错误摘要。这里是完成申请，不允许 Worker 直接设置 succeeded。请求／解析失败、取消或合法零产出也须如实声明，不能因为没有代理记录就省略结束反馈。

服务在短写事务核对：1 到 last_batch_no 均已提交、各类记录数一致、本轮仍允许收尾、页面最终结果及摘要相符、结束原因符合本轮输入范围。全部必要步骤正常结束且输出完整，才提交 success；有正常产出及必要页面／解析失败可为 partial；明确错误／取消分别记录 failed／cancelled；自然结束但无代理显示 zero_output，不凭零产出断定解析器坏，也不显示为有代理的健康成功。跳过与失效另保留明确原因。

正常完成申请缺包或计数不符返回 INCOMPLETE_UPLOAD／COUNT_MISMATCH，不能成功；可在期限内补原包再收尾。明确失败／取消的收尾可以记录已保存部分和缺失原因，不能为了等待无法恢复的包永久保持运行。最终更新、完成确认摘要和必要的同库下一步输入在一个事务提交，返回 committed=true 与服务判定的 outcome。已入库有效部分不全盘回滚。

相同收尾内容重传返回同一最终确认；不同内容冲突。完成后不再接收新增结果包；已提交包重传仅确认原事实。批次及收尾凭证至少覆盖约定的重试窗口，同时有条数／时间上限；保留期和旧运行删除要一同核算，不能提前删凭证还承诺重试幂等。旧运行记录已清理后不因迟到 start 重新创建，平台终态及允许窗口校验要拒绝陈旧调用。

### 缺反馈和程序收尾

开始、数据包和 finish 都等待统一写入口提交；公共 Pipeline／收尾适配负责重试及排空，网站脚本不重写协议。复用 [Pipeline](https://docs.scrapy.org/en/latest/topics/item-pipeline.html) 和 [spider_closed](https://docs.scrapy.org/en/latest/topics/signals.html#spider-closed)，但不能假设任意解析错误都会自动变成进程非零退出；共享入口须收集错误并明确报告。

现有服务按已知任务和截止索引小批核对：平台 failed／cancelled 或运行超过硬期限，复核已经提交的包后记录明确非成功结果；平台 finished 但缺 finish，只在有限回调宽限期内等待／补查，超期记缺结束反馈，不自动补成功。已经业务确认成功后，平台稍晚报错也不能抹掉提交事实；它是平台异常，单独可见。任务恢复通过新 task_id 按策略发布，旧回调只作用旧运行，状态不回退覆盖新任务。

不增加独立心跳／恢复容器。起止仅少量关键写入，结果按包写，任务身份用平台现成 ID；队列条数／字节／等待、包大小、运行硬期限、回调宽限、重试次数与凭证保留均配置化。最终 SQL 表结构／配额留 M05，运行验证仍未执行。

## 主动测试任务

用户明确测试闭环：M04测试系统从M05取得本轮需要测试的代理＋目标组合，M05在返回前持久标记为待测试，再由M04发布到Crawlab；Worker处理后直接回传M05，M05更新状态和结果。下一轮重新向M05获取需要测试的内容；Worker不自行重新安排或重跑测试任务。选测规则必须考虑已安排状态，避免重复发布。

### 已确认流程与边界

M04发起本轮选测请求 → M05提交本轮固定成员及待测试标记 → 返回给M04 → M04按同target_id／revision／请求配置的小批发布Crawlab → Worker执行本次访问并直接回传 → M05提交结果和成员状态 → 下轮重新选测。

一个平台小任务可包含有限多个测试成员；例如100项是批大小示例，不是100次原生进程启动，也不等于HTTP并发100。一次代理＋目标测试有独立check_id／成员身份，新一轮重新测试使用新身份。Worker不因访问失败或任务中断自行重跑同一测试；是否需要再次测试由后续选测判断。已有结果的传输重发与重新发起网络访问是两回事，前者的有限重发机制仍待确认；如允许重发必须保持原身份和内容，不重复计分。

### 建议：将业务到期与本轮占用分开

以下是落实上述流程的建议，尚未确认表结构、状态名和数值。需要测的单位是(proxy_id, target_id, target_revision)，不是代理全局状态。候选须同时满足目标启用、端点有效、测试策略到期、无有效在途成员及本轮预算；目标停用或规则变化后重新核验。

- 未有有效观测的代理／新目标配置：进入预热候选。
- 最近有成功访问且没有更新的失败：暂不重复测试，真实调用反馈与主动测试共同提供观测。
- 历史可靠但最近一次失败：允许提前复核；只降低质量，不直接暂停供应。
- 普通到期或低质量组合：按配置安排常规／较低频复测，不无限占用测试预算，也不永远没有复测机会。
- 已经待发布、已发布或执行中的有效成员：本轮排除。最后发布／选取时间不冒充成功或失败观测。

可考虑维护next_check_at、active_check_id和check_deadline_at等少量当前字段，替代每次扫描全部历史；它们是字段候选。间隔、失败复核条件、组间预算和期限待后续确认，旧稿5min／1min／30min等均不是已确认默认值。不要预先物化全代理×全目标组合。

### 建议：同一短事务内选取并标记

建议由M05提供testing.reserve_checks(target_id, limit, now)，在统一单写入口完成：核验配置／预算 → 按索引有限选取到期且未占用成员 → 保存本轮成员及待测试标记／期限 → COMMIT → 返回本轮ID和输入。reserve_checks不是只读查询，成功响应必须在事务提交后；不采用SELECT返回给发布端、发布后再标记的分离流程。选测策略归M04业务规则，M05负责数据库执行和一致性，不新建调度服务。

```json
      "usage_id": "00000000-0000-4000-8000-000000000204",
      "observed_at": "2026-10-24T08:01:00.000Z",
      "request_url": "https://example.invalid/check",
      "outcome": "response",
      "http_status": 200,
      "error_code": null,
      "latency_ms": 420
    }
  ]
}
```

一次真正的网络尝试一个 usage_id。同一 member 可在 use_before 前实际使用多次，每次新 ID；网络上传重试沿用原 ID。服务推导 producer_id=caller:<认证身份>、observation_id=usage_id、origin=usage，校验批次归属、成员、URL origin、network_scope 和目标快照；不接受客户端改 proxy_id、target_id、revision、success 或 score。

首次上报 observed_at 须在批次 [created_at−60s,use_before] 内，符合全局未来／迟到限制；同一记录重放不重新判断为一次新失败。旧 target revision 或已删除网站的有效批次反馈可以接收，但只写短期凭证并计入 obsolete_target，不重建旧样本／质量，不影响新 revision。

| outcome | http_status | error_code | latency_ms |
| --- | --- | --- | --- |
| response | 必填，100—599 整数 | null | 必填，≥0 的整数，响应头耗时 |
| proxy_error | null | proxy_connect_failed／proxy_timeout／tunnel_error／tls_error 之一 | 必填，≥0，至失败的耗时 |
| execution_error | null | node_offline／dependency_error／invalid_request／local_io_error 之一 | 可为 null |
| cancelled | null | caller_cancelled | 可为 null |

禁止同时声称收到 200 又使用 proxy_error。代理连接／目标访问超时都可计作 proxy_timeout，表示路径访问失败而非认定根因；明确节点本地离线则 execution_error。调用方正文解析或业务处理错误不伪装成代理失败。

任何字段不合法整包 422；同 ID 不同事实整包 409；整包通过后在同一数据库事务中写短期凭证、更新适用组合并修剪旧样本。execution_error／cancelled 不增加样本行，仅写凭证和最近诊断。原样本已被淘汰时也必须先查凭证，不得把重传重新插进样本。相同记录重复提交返回 200：

```json
{
  "accepted": 1,
  "duplicate": 0,
  "scored": 1,
  "ignored_for_quality": 0,
  "obsolete_target": 0
}
```

accepted／duplicate 按本包记录计数。先区分 obsolete_target，再将当前配置下的新结果分为 scored（response／proxy_error）或 ignored_for_quality（execution_error／cancelled），所以 accepted=scored+ignored_for_quality+obsolete_target。scored 不表示一定保留该样本：旧于 24h、或不属于最近 50 条时只保存凭证；结果已按规则处理，不能据成功响应声称有完整历史。没有使用或没有反馈时无需占位记录，不把剩余成员记失败。

凭证固定到期于所属批次 use_before／execute_before+48h，全局最多 2000000 条；批次最多 250000 个、成员最多 2500000 行。晚到不延长保留，用同一截止便于核算容量并先子后父清理。清理到期凭证后仍放不下整包净新增时，整包返回 503 CAPACITY_LIMIT，不提前删除有效凭证，不返回成功后漏记。未超过固定保留期的纯重复包仍可确认；超过 retained_until 明确拒绝，不保证无限期重复确认。其他容量、长度与预算以存储方案为准。

## 结果导入与持久化边界

原生结果优先路径：Scrapy／普通测试程序 → 选定版本配套的 Crawlab 结果 SDK → 按原生 task_id 查询 → importer → 业务数据库。采用哪个 SDK／IPC／gRPC 适配仍需验证；业务字段先固定，不猜测平台原生传输字段名。

本轮已核对官方 crawlab-python-sdk 固定提交 167b84859b57ac247e3409b5ef09c1e1ad5ddac2：save_item(*items) 输出 ipc=true、type=data、payload 的 JSON 行，Scrapy 入口是 crawlab.CrawlabPipeline。该 IPC 包装由配套 SDK 生成，业务不另造结果传输；普通日志继续是日志。stdout.flush 不是平台持久化 ACK，SDK 发行版本与运行镜像仍需配套验证。

导入器核验任务来源、允许程序、成员和 revision，从平台上下文取得 task_id／node_id；剥离平台自动加的已知元数据后校验 v1 业务字段，不能因为业务未知字段严格校验而拒绝平台的合法包装。未完成导入阶段每 (task_id,record_id) 保存有限摘要，重复相同跳过，冲突记录并阻止该包推进；凭证不附代理 ID、host／port 或来源页面 URL，不用凭证另建代理来源索引。测试结果的访问去重由 observation_receipts 继续保障。任务完成且核对记录数后可清逐条 import_records，保留有限完成摘要，自动导入不再重扫已完成／已淘汰旧任务。

每包最多 500 条，解析和网络读取在事务外，业务变化与 import_records 同事务提交。分页 offset 不是持久数据身份；结果集合增长时重新从前面扫描并去重，不只保存一次扫到的页码。业务接收成功仅表示已入业务库，平台结果的持久完整性还要独立验收。

来源运行：有完成摘要时核对 distinct proxy／page 记录数与 expected_* 一致。主动测试：成功结束时应有所有成员的 check_result 才标记导入完整；异常／过期有缺失成员时保留 partial，并按平台状态释放在途关联，不合成失败观测。缺摘要、缺成员、计数冲突和平台异常都显示 pending／partial／error，不以任务 finished 或“两次 total 一样”冒充完整。异常运行仍保留已经导入的有效结果，不全盘回滚其他页面的发现。

来源发现结果的异常重查期建议 7d；主动测试新结果接收期为 24h，超过后显示超期未评分／部分导入，不合成失败，不重建已清理评分。未完成导入也受凭证／运行总量限制，满时停止接纳新任务或新导入包并显示容量。超过重查期保留有限异常摘要、人工核对；不为腾空间默默标成完成。历史重放不属于自动流程，需另行明确范围。原生通道不满足时再选单一最小补充，不预先实现两套，不承诺恰好一次执行。

业务库有界不等于平台结果与日志已经有界；Crawlab 自身的结果保留、容量和清理能力需随所选版本验收，已完成并核对导入的结果才可纳入安全清理，未导入结果不能被静默淘汰。

## 错误、重试与兼容

SQLite 队列反馈补充：队列和等待必须有界，入队满额／超时预期返回明确可重试错误而非先 202 确认，客户端保留原身份。请求断开不证明事务已撤销，重复请求必须查持久凭证；完成通知不得越过尚未确认的数据包。关键开始／停止／完成操作触发及时 flush，仍经过统一写入口。分发批次及成员持久提交后才发给调用方，不能以“读取代理”为由绕过写入一致性。合批只改变提交组织，不改变每条真实观测身份与全包原子约定。

### 逐业务 URL 的可恢复确认：修订候选

状态存储最新讨论：Worker 经业务 API 更新并查询状态，状态写入持久库，不仅写服务内存。当前候选沿 Proxypool SQLite 的来源运行／测试批次记录，关联原生 task_id；未决定增加 Redis。状态写入核验本次运行／批次及允许转换，完成状态由服务在结果持久提交后确定，不允许客户端任意覆盖 succeeded。每次运行独立，重复和迟到更新不能覆盖新一轮；内存合批不能提前确认关键状态。原生执行进度与业务提交事实分开，其他应用按相同反馈原则写其自身业务库。

当前反馈讨论入口：用户明确保留 Crawlab，现先讨论公共执行适配 → 业务持久确认 → 原生进程终态的链路，不以更换框架作为前置条件。候选 POST /internal/v1/crawl-results（路径未定）按平台 task_id、业务输入及本次执行关联校验逐输入结果，以稳定请求身份处理重传。业务服务同事务提交数据和完成标记后才确认，较大数据分包后以最终摘要核对，失败不以 received 冒充 committed。正常业务失败可明确上报；平台 finished／error 仅辅助核对，不能覆盖已提交事实。字段、权限、版本／迟到保护、查询期限与重试仍需逐项确认，不表示本文已经实现写入口。

上一轮成熟框架研究保留：本节自建状态／generation／start 接口仍是未采纳备选，暂不作为首版必需协议。Feapder／Crawlee 的研究见 [框架复查](../framework-references.md)，当前讨论以 [M03 反馈方案](../../plugins/README.md) 为准。是否继续 Crawlab 中转或改为公共 Pipeline 等待业务写入确认仍待选择，不能未经确认同时建立两条主写入路径。

用户指出平台 finished 不能确认每条输入已落库或不会永久卡住。本段为这一明确需求补充候选协议，具体字段仍待 M05 审阅，尚无实现或旧客户端。发布参数或认证输入提供 work_id、generation；合批仍保留逐输入身份。候选 POST /internal/v1/crawl-work/{work_id}/start 接收 generation／原生 task_id，服务核验平台关联后原子绑定执行者和有限期限。成功授权才发请求；同轮同 task 的幂等重取不能无限延长期限。该 Worker 权限扩展原先只读输入范围，仅限必要执行确认，不允许自报 succeeded 或任意改分，也不自造平台节点领取。

回传继续用配套 SDK／平台结果，候选增加 crawl_chunk、crawl_complete 受控包装。chunk 含 work_id、generation、稳定 record_id／chunk_seq 和有限 items；complete 含同一上下文、逐输入处理结果、必要请求／解析结果、expected_records 和合法空结果声明。上下文仅用于有限导入及当前状态，不复制到代理行；凭证不附端点明文，不新建代理来源映射。

导入及最终事务内核验当前 generation、task_id、状态和服务器期限。必要输出与完成摘要齐备且本阶段处理成功，才同事务提交最后数据、succeeded 和同库下一步输入；数量冲突、缺摘要、解析失败、不允许的空结果不标成功。此前可以分批入库，但保持 importing；失败不 ACK 成功，不能按平台总数或一个 URL 成功批量完成全部 URL。

dispatching、queued、running、importing 都有有限阶段期限与本轮硬上限。reconcile_due 小批先补查已有结果，能完成则提交，否则记录错误并撤销该轮写入资格，再有界退避重试或停在 failed。发布响应不确定先核对，超期也必须使旧轮失效，不无限等待或直接重发仍有效的同轮任务。旧任务迟到不得更新当前状态或生成下一步；已成功同内容重传可确认已处理。可能重复抓取，不承诺网络请求恰好一次。

周期来源本轮根输入也需工作记录才能确认业务成功；其与原生 Schedule／批次关联按所选版本验证。上述设计只补必要业务状态，不强制所有其他应用实现通用 JobSpec，详见 [M03 闭环](../../plugins/README.md)。

M03 完成与启动边界（讨论建议）：同站分页由普通 Scrapy 请求流处理；平台的 finished 只表示进程结束，不表示每页成功或业务数据已完整。M05 依完成摘要、记录数和逐项结果核对导入，再由相应业务判断是否产生下一阶段待处理输入。后续输入依赖整批还是独立单条须由业务约定，均不得在结果持久提交前发布。当前任务不等待无限后续周期或所有后代任务才结束。

暂停业务发布只阻止新发布，已接收任务默认继续，待发布输入保留在业务库；原生 Schedule 需另同步 enabled 才会停止周期。平台接受响应不确定时保留待核对，不能直接回到未发布盲重试；本地数据库事务不保证平台发布原子性。发布端与导入逻辑职责可独立，但不强制分服务；进程都停时依持久状态恢复。以上关闭／恢复语义尚待用户确认，具体业务标记留相应模块确定，不新增统一 JobSpec 或通用领取回执。

错误格式为 error 对象，字段 code、message、retryable、trace_id；message 脱敏。400 用于不能解析的请求，401／403 认证／授权，404 对象不存在，409 业务冲突／停用／过期任务，412 配置条件更新冲突，413 包过大，422 字段／时间非法，429 服务限流，503 暂时无法提交。429／503 可返回 Retry-After。

调用方仅对网络中断、429、503 做有上限的指数退避重传，沿用 request_id／usage_id。收到 409 或 422 不通过换 ID 掩盖错误。来源发布动作不因超时盲目重试：先查平台任务再处理，平台本身不是本协议的幂等 HTTP 写入方。

v1 对未知字段严格拒绝；新增可选字段也应先升级接收端并验证兼容，再升级发送端。不兼容修改使用 /v2 或 schema_version=2。接口协议版本、目标 revision、评分 policy_version 和来源修订分别表达不同含义，不混成插件版本体系。

## 原始 HTML 的边界

本协议明确保留跨设备解析：同进程可用 Response 内存；跨设备必须先持久保存原文，再发布引用文件 ID 的解析任务。原文元数据需包含 ID、来源、URL、内容类型、编码、时间、摘要，仍在途引用的文件不清理。

原文上传读取接口不属于本次代理存储／反馈 v1 的已定内容，应在分步解析阶段具体设计；不能宣称本协议已经覆盖整个文件系统，也不能把 Scrapy Feed exports 当原始 HTML 保存。它不影响当前抓取、测试、分发和反馈的数据约定。
