## Wilson评分与63位窗口复述（2026-10-29，用户指定沿用算法并要求最后核对）

用户指定沿用此前讨论的Wilson算法，并提出充分利用整数的63位；本轮以Wilson下界×100、最近63次有效访问作为具体重述。z建议默认1.96并配置化；首版整数窗口N=63，sample_count另存实际样本数，最多63。首次无样本score=NULL，有样本全失败score=0。SQLite有符号64位整数以非负值使用，可容纳2^63-1；已有50位值可能也占8字节，扩到63位不增加字段，但不是每个值都固定占8字节或整行仅8字节。63次比50次保留更多证据、反应稍慢，稳定优先场景可采用；本轮等待用户对复述最后核对，未改代码。

```text
bits = ((bits << 1) | success) & ((1 << 63) - 1)
n = min(n + 1, 63)
s = bits.bit_count()
p = s / n
score = 100 * (p + z*z/(2*n) - z*sqrt(p*(1-p)/n + z*z/(4*n*n))) / (1 + z*z/n)
```

在Python中计算并掩码后保存非负整数，反馈顺序沿已确认M05处理／成功提交顺序，同包按输入顺序，重复不移位。仅按次数滚动，不添加逐条时间数组或时间过期规则。分数作为保守排名，不等于下一次访问概率保证；速度EWMA仍独立、同分时参考，不添加主观扣分或混合权重。累计feedback_count与位图长度无关，最低淘汰次数仍配置化，不因窗口改63而自动改门槛。

本机独立算例z=1.96：1/1=20.65，10/10=72.25，57/63=80.74，62/63=91.54，63/63=94.25，0/63=0。原PoC wilson_preview函数、50次逐条记录及旧schema均未改，本轮只有数学重算与设计更新。参考[NIST Wilson](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)和[SQLite整数类型](https://www.sqlite.org/datatype3.html)。较早50次／24h的研究示例保留历史含义，不作为新的逐条过期要求。

## 按实际读写场景收敛的存储推荐（2026-10-29，助手综合建议）

用户要求结合抓取、反馈、选测、获取和淘汰给出最合适方案。本节记录综合建议，未因此把所有字段／索引标为用户逐项确认；当前仍只设计，不改业务代码、schema或服务器。用户此前已要求取消代理主表次数更新、去重只留短期内存；本节同步覆盖旧数据库凭证建议。

### 三张核心表

- proxies：整数proxy_id，scheme、host、port及其唯一约束；只保存端点资料，不保存来源、发现时间或每次反馈都要更新的全局计数。整数ID用SQLite标准主键生成，正式ID表现与旧PoC不同的部分实施时再对齐。
- targets：目标ID、名称、测试URL、启用开关及当前配置revision。建议正式内部目标ID也用整数减少重复键体积；API字段最终类型仍待协议收敛。来源网页请求头放对应脚本，目标自测请求头和默认超时放测试配置／代码；数据库只保存需要前端动态管理的目标内容。
- proxy_quality：每个代理＋网址只保留当前一行，字段为target_id、proxy_id、target_revision、result_bits、sample_count、feedback_count、score、successful_latency_ewma_ms、last_feedback_at、last_test_scheduled_at。推荐PRIMARY KEY(target_id,proxy_id) WITHOUT ROWID，按网址组织主表。sample_count是有上限的位图样本数，feedback_count是该组合累计有效访问数；后一字段与本行同一次更新，不再额外写代理主表。淘汰时SUM(feedback_count)，不把窗口封顶数假称终身次数；删除／重置目标质量后的聚合只反映仍保留的组合统计，不承诺保留跨已删除目标的终身累计。

必要的两个辅助索引：quality_rank(target_id,score DESC,successful_latency_ewma_ms ASC)用于候选筛选／排序；quality_proxy(proxy_id)用于按代理反查、外键级联删除，避免删除一批代理时逐次扫描整张网址优先的质量表。第二个索引是综合删除业务后的推荐，尚未包含在此前布局微基准中。不给两个调度时间各建索引，不增加常驻总分字段。

### 五条业务路径

| 路径 | 读取及写入方式 |
| --- | --- |
| 来源抓取 | 每来源回传一批端点，M05按唯一约束批量去重／新增proxies；重新发现不重置质量、不增加次数，不立即建立代理×全部网址矩阵 |
| 访问反馈 | 统一入口、内存result_id去重，按队列顺序合并同组合结果；更新位图／次数／评分／成功耗时／反馈时间，只写受影响质量行 |
| 主动选测 | 单发布实例逐网址读当前质量轻量字段；没有质量行的代理按未测试处理，可从proxies反查缺行成员，不读取其他网址历史；切批发布成功后批量UPSERT安排时间，保存实际安排时刻而非稍后的提交时刻，不覆盖已回传评分 |
| 获取代理 | 按目标和最低分沿排名索引取有限批，按入选proxy_id查询地址；在M05有限内存缓存打乱pop，空或过期才补充，不每请求查库／计算分数／登记使用身份 |
| 轮前淘汰 | 发布抓取前，对当前参与评价的目标质量一次GROUP BY proxy_id汇总分数及次数，筛选门槛后取超量末尾；不为低频聚合增加每次反馈同步更新的总分／全局次数 |

质量行在首次安排或有效访问时按需创建；首次新网址要识别全部未测端点，但不要求全量矩阵预建。目标停用保留数据、暂停测试与获取；修改影响评价的测试配置时版本更新并清理／重置该目标旧评价，不累积历史版本；老版本反馈不能混入当前评价。仅改名称不重置。删除端点／目标时删除关联质量，均由同一个写入口执行，较大清理按有限批提交，M03待本轮要求的清理完成才发布。按代理查找索引的必要性是本次五路径综合评估的一部分，不另加通用任务系统。

### 写入与内存

复用已选定单M05进程、有界queue.Queue、一个写线程和独占写连接。使用WAL，建议先保留synchronous=FULL，不用放松提交持久性来宣传性能。普通发现／反馈按条数或首项等待时间合批；安排时间等及时操作触发当前顺序上的尽快提交。读取独立连接，只看已提交数据，接受队列等待与候选缓存造成的滞后。

反馈去重完全改为进程内短期ID记录，不查询或写入SQLite receipts表。等待提交的同ID共用处理结果；COMMIT成功后短期保留已处理ID供有限重传命中，提交失败不标为已成功。复用允许重传的短期等待窗口，到期清理并有数量上限，不新增接收期限或completed_at。重启／内存记录淘汰后可能重复计分，按个人场景接受，不建设持久补偿机制。result_id由执行侧生成，获取代理不预登记凭证；此修订不改变反馈提交后才回复成功。队列、单包和候选缓存沿既有容量配置，不引入Redis。

## M05统一写入入口（2026-10-29，用户授权助手确定设计）

本节是本轮选定的实现方向，非运行事实：一个M05业务进程、一个有界queue.Queue、一个后台写入线程。写线程创建并独占SQLite写连接，所有业务INSERT／UPDATE／DELETE都经过它；API及读取连接不直接修改数据库。无需Redis、独立队列容器、额外写入进程或自建锁框架。当前不部署多个M05 API进程各带写线程；并发HTTP请求不等于多个业务进程。

### 数据流与方法职责

```text
API校验并入队 → 写线程收集一批 → 短事务执行并COMMIT → 通知对应请求成功
                     ↑
               本批写入期间，新请求继续入队等待下一批
```

拟定方法名仅表达职责，不创建通用插件／SQL执行协议：

| 方法 | 职责 |
| --- | --- |
| import_proxies(proxies) | 来源发现按端点去重、新增；放入统一队列 |
| submit_feedback(results) | 自测／实际使用统一反馈入队；有限重传沿用result_id |
| mark_tests_scheduled(proxy_ids, target_id, scheduled_at) | 发布一批成功后保存该批安排时间 |
| enqueue_write(kind, payload) | 内部入队并返回供本请求异步等待的完成通知 |
| writer_loop() | 写线程等待队列、按时间／条数取有限批次 |
| commit_batch(batch) | 事务内按顺序处理，成功提交后完成通知；失败回滚并通知失败 |

目标配置修改、删除／容量清理也复用此入口的明确业务操作，不允许外部提交任意SQL或函数。时间字段使用已确认双时间模型，不恢复active_check_id或测试状态；单实例M04依然发布成功后更新安排时间。

### 合批与队列

普通发现和反馈按配置的批记录数或从首项入队起的等待时间触发，任一先到即提交；10秒仅为已有示例，不是硬编码。等待期间不开事务。写线程取出本批后立即释放队列内部锁，数据库事务期间不占队列锁，因此API仍可入队。剩余项保留原入队时间，不把新一批开始收集时间当作等待起点，避免长时间推迟旧请求。

安排时间和配置变更等需及时生效的操作到达时，触发把它及之前的队列内容尽快提交；不越过前面的操作建立另一条写通道，不必强等完整普通合批窗口。按FIFO维护业务操作顺序，批内合并同组合多条反馈时保留每条有效结果先后；合并不能跨过对该组合的删除／配置变更操作。只更新操作负责的字段，不用旧整行覆盖反馈时间／安排时间。

队列满额返回明确繁忙错误，API不无限等待队列空位，也不持锁等待磁盘。配置queue_max_requests、max_request_records、max_request_bytes、batch_max_records和flush_interval_s；请求数及单请求条数／体积共同限制内存，批大小限制单次事务工作量。超过单请求上限由发送端切包，不以一个超大请求绕过批次边界。批次先按包组合，记录数不能超过配置批上限；单包记录上限不得高于批上限。配置取值根据实际设备和后续负载调整，不要求用户逐个给数值。

### 事务、读取与响应

有限二元历史、评分、成功耗时EWMA及最新反馈时间同事务提交；反馈ID改为内存短期去重，提交后标记已成功；同组合多条反馈先顺序合入，允许最后一次保存汇总，不丢中间访问。重复结果不再次计分或更新时间。本批出错则回滚该批并向相应请求返回失败，仍用原结果身份有限重传；不额外建设逐条故障隔离／持久重放系统。

响应只在COMMIT成功后返回committed=true；API以异步完成通知等待，不同步阻塞整个接收循环。通知是进程内部协调，不新增Worker确认接口／额外握手。普通入队成功不冒充已落库。发送端按小包回传并等待提交，避免每测一个都串行等待一个合批窗口。

读取使用独立连接，仅看已提交SQLite数据，不查内存写队列。使用WAL，连接按实际线程归属创建／复用，不跨线程共享写连接；读请求也不排到写队列。读取可能看到当前提交之前的快照，代理缓存又可能保持至下次补充，接受这个已有的有限滞后。无依据宣称每次读写均绝不等待；索引、连接数、事务时长和WAL占用待实现时验证。

正常关闭时停止接纳新写请求并尽量提交已接纳队列后关闭连接；异常退出允许丢失未提交内存内容，沿用已确认有限重传和双时间timeout恢复，不增加持久消息队列。后台线程空闲时阻塞等待，不忙轮询消耗CPU。常态资源是一个服务进程、一个写线程、有限队列与连接；峰值由上述请求／批次上限控制，尚无新增服务器性能实测。

本轮仅更新设计。原PoC源码、旧schema及106项历史检查仍按原范围解释，未实现后台写线程／合批队列，也未迁移、运行新测试或部署服务。参考既有标准能力：[SQLite写事务](https://www.sqlite.org/lang_transaction.html)、[Python 3.10 queue.Queue](https://docs.python.org/3.10/library/queue.html)。本节覆盖下文较早对写入线程／批提交方式的候选描述，保持无反馈接收期限和不新增边缘防御的用户约束。

## 反馈有限重传与短期去重（2026-10-29，用户确认）

## 成功响应速度的有限存储方案（2026-10-28，用户确认）

用户回复“就按你说的来吧”，确认每个代理＋测试目标维护一个成功耗时EWMA值，alpha配置化；首次有效成功耗时初始化，后续按已确认的处理顺序更新，失败／重复不更新该值，没有成功耗时则为NULL。稳定性优先，同分再比较速度，不把跨网址耗时加入整体淘汰总分。以此取代精确窗口中位数的推荐，避免为速度保存50条原始耗时。本轮确认设计，已有PoC的latency_median_ms字段及公式不修改，正式实现／迁移后续另行处理。

[NIST EWMA](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc324.htm)定义E_new=(1-alpha)*E_old+alpha*x。首次有效成功用其耗时初始化，后续按M05已确认的处理顺序合入有效成功耗时；无成功时为NULL。失败仍更新成功率证据，执行／回传错误不伪造成功耗时；重复反馈不再次平滑。alpha是配置参数，本轮不围绕具体取值追加产品决策；普通按次EWMA也不会在无新成功时自行随时钟变化。

资源取舍：最近一次耗时和EWMA都只需一个标量、每次更新计算量固定；EWMA对单次波动更平滑。精确最近50次成功耗时中位数需保留相应原始值，按50个32位毫秒槽估计最多200字节原始载荷，尚有数量／空值等元数据；EWMA以一个通常8字节的REAL取代这些槽，属于有损汇总，不等价于中位数，也不能回放原耗时。50项的排序本身不必然是CPU瓶颈，主要节省的是数据保留及维护；完整库大小／吞吐没有本轮实测。

业务使用建议：每个目标单独计时，成功口径和计时范围保持一致，不跨不同网站直接比较绝对毫秒数。稳定性分数优先，同分时耗时低者在候选排序中靠前；随后沿用有限候选批次的随机取用。轮前容量清理仍沿用各目标稳定性总分方向，不把不同网站耗时再加权进全局总分。EWMA可与位图、数量和评分在同一个已有写事务／批次里更新，不新建耗时明细表、写事务或常驻服务。该速度设计已按用户确认，未实现、迁移或操作服务器。

## 最近50次的位图存储研究（2026-10-28，未选定实现）

用户提出以1／0编码成功／失败并进行FIFO，避免只留成功数／总数后无法确定淘汰哪一次。该方向可行，准确说法为位图；十六进制只是显示，建议直接存SQLite INTEGER，每项占1 bit，不是每项占一个十六进制字符。不要求50条SQL行，位图本身已经保留顺序。

右侧约定为最新结果，N=50：bits=((bits<<1)|result)&((1<<50)-1)，n=min(n+1,50)，s=bits.bit_count()；将s和n交给Wilson即可。掩码截掉最旧结果，无须判断应该淘汰成功还是失败。有效长度必须另外编码，推荐单独sample_count；bits=0既可能无样本，也可能有50次失败，不能用bit_length推断数量。低位可直接得到最近一次／最近若干次结果，供近期失败优先复测，不新增供应暂停状态。

- **速度统计（已确认）**：采用一个成功耗时EWMA标量，bit仍只记录二元结果；无需为了速度保存逐项耗时，也不再提供精确窗口中位数。每次回传仍传本次耗时供更新，正式持久字段与协议见本节顶部的已确认方案。
- **重复反馈**：位图不表示请求／结果身份，短期去重凭证和测试占用关联仍保留；同一事实重复回传必须先去重再移位。位图、长度、分数和真实反馈时间应在同一事务提交，批写仍按受影响组合聚合。

如需逐条时间及精确中位数，可研究每组合一行：result_bits＋sample_count＋有界timestamps／latencies BLOB，而非每项一行。以50个64位毫秒时间戳和50个32位耗时槽为示例，元数据原始载荷约600字节，另加位图／长度及数据库开销；这是编码预算，具体空值、版本、排序和更新格式尚未设计。读取／修改整段BLOB的成本、SQL查询便利性也须比较，不能只按位数判断优劣。该600字节示例是旧精确中位数候选的成本比较；速度现已确认EWMA，不需要其中的逐项latencies槽，时间元数据是否保留仍独立讨论。

本地隔离验证（非实现）：Python3.13.14／SQLite3.53.1，515组序列、13861次更新，对照有界队列验证SQL移位及Python位图一致，覆盖前导0、全失败、全成功、溢出淘汰、十六进制文本陷阱和乱序差异；临时库已清理。没有迁移schema、改业务代码或访问服务器，未声称已在服务器SQLite3.31.1运行此实验。计算与存储载荷可以简化，但SQLite按页写入，不能据8字节推算每次仅8字节磁盘I/O或承诺整套服务加速倍数；吞吐仍待实测。

当前建议：将位图作为二元历史的首选压缩候选；FIFO顺序已按用户确认统一为M05处理并成功提交先后。速度现已确认使用EWMA；后续按逐条时间过期等剩余信息需求选择纯INTEGER版或附时间元数据版。不把本次研究自动改成已确认的存储或评分方案。

- [Python3WebSpider/ProxyPool测试器](https://github.com/Python3WebSpider/ProxyPool/blob/cabcd96cc9f30d7bdbc872bb8a8c52760023c142/proxypool/processors/tester.py)及[存储计分](https://github.com/Python3WebSpider/ProxyPool/blob/cabcd96cc9f30d7bdbc872bb8a8c52760023c142/proxypool/storages/redis.py)：默认成功恢复最高分，失败扣1，到下限移除；有不恢复满分的配置。可借鉴简单维护入口，不能把这种分数解释成成功概率。
- [jhao104/proxy_pool](https://github.com/jhao104/proxy_pool/blob/9cc0cad4c47e84e34aaec2eead099421960dcd07/helper/check.py)：成功减少失败计数，失败增加，并以阈值决定删除；其fail_count不是累计失败样本数。[#512](https://github.com/jhao104/proxy_pool/issues/512)反映单次失败删除的使用问题，失败比例阈值及性能为发帖者经验，不作为普适结论。
- [haipproxy](https://github.com/SpiderClub/haipproxy/blob/ab30ccf4b1d78e9304c27830006cc5800fe41bb3/haipproxy/crawler/pipelines.py)：维护分数、最近验证时间及速度，采用加减分及低分删除。可借鉴维度独立，删除规则不照搬。
- [NIST Wilson](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)和[Evan Miller排名分析](https://www.evanmiller.org/how-not-to-sort-by-average-rating.html)：成功比例结合样本量形成保守排名，适合稳定优先且不让单次成功达到满分。
- [NIST EWMA](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc324.htm)：E_new=alpha*x+(1-alpha)*E_old，强调新观测；直接作为二元结果排序是本项目可评估的应用，不照搬原控制图的正态控制限。普通按次EWMA无新观测不会自动随时钟衰减，也不单独表达样本不足。
- [贝叶斯二元评分](https://www.evanmiller.org/bayesian-average-ratings.html)：可显式选择先验和风险偏好；适合后续确有该需求再评估，当前不同时引入第二套主评分。

建议仍是按代理＋目标revision维护有限近期样本，使用下文标准Wilson下界；N=50、T=24h、z=1.96保留为可配置的初始实验建议，未确认最优。24h是样本绝对上限，不代表该代理24h内持续可靠；自测间隔另按真实反馈时间安排。只在同一测试语义及认可的网络范围内合并主动测试和调用反馈，同一事实只计一次，执行／回传故障不伪造代理失败。

Wilson只看窗口内成功数与样本数，同样计数但失败顺序不同会得到同分，不能声称自动识别刚发生的恶化。历史较好而最新失败时提高主动复测优先级，不新增暂停供应状态；如果实测仍反应迟缓，先比较更短窗口，再单独评估EWMA，不直接叠加拍脑袋惩罚系数或把加权计数当标准置信区间。

score不是下一次成功概率。代理结果可能相关且随时间／执行网络变化，仅作为经验排序，不能按z参数宣称个体下一次成功保障。保留实际成功率及样本量供解释；样本全部过期为未知，维护重算不刷新最近真实反馈时间。过期失败被淘汰也可能使分数上升，分数不是固定加减积分。

速度已确认以成功请求耗时EWMA单独记录，稳定性同分时比较，避免把慢而可靠的代理被一个任意加权总分压低。数据库合批时对受影响组合统一修剪、汇总并计算一次；每组合最多50条是该参数下的行数上限，统计排名不需要新增Redis或统计服务，也不需要为计算分数额外制造网络请求。空间上限仍按组合总数和短期凭证共同核算；本轮未做资源／吞吐测试。

## 推荐结论

候选 A 的存储取舍（2026-10-25，未确认）：Worker SDK→Crawlab 原生结果→M05 有界导入→SQLite，可复用原生中转而不额外要求业务回调。平台管理执行状态，M05 只保存必要输入、关联及业务入库事实；固定成员／摘要未齐时不能因平台 finished 就成功。平台暂存和 SQLite 双份写入／空间及清理是该路径的明确成本，仍须与直接回传比较。原生 SQLite 适配的逐条插入及错误语义不能承担我们的幂等／质量事务，也不直接增加第二个主库写入者。取舍分析见 [方法设计](../../apps/proxypool/design.md)，下文直接业务回调属于候选 B；两者均不改变用户已接受的 SQLite 业务存储和唯一写入口。

2026-10-25 新方案评估：用户提出来源直接回传 JSON、同目标 URL 代理切小批测试、按目标内存获取队列、首个写请求起 10s 收集窗口和统一前端。完整用户设想及助手修正集中在 [方法设计](../../apps/proxypool/design.md)，尚未全部确认；直接 JSON 回传属于候选 B，不据此撤销候选 A。两者均使用有限小任务，不再把每个代理一条平台任务作为默认粒度。

两类高频内容是端点发现和真实访问观测，不意味着只有两类数据库写入。来源／目标配置、运行进度、批次及成员、幂等凭证、删除和容量维护也经同一写入口。端点规范化后以唯一键和 SQLite ON CONFLICT 处理批量去重，不先为每条查一次再插；数据重复不降低来源运行健康。去重观测及更新质量、进度和必要终态同短事务提交。[SQLite UPSERT](https://www.sqlite.org/lang_upsert.html) 支持唯一冲突时跳过／更新；网络／等待在事务外。

10s 目前是用户提出的收集窗口设想，不是已确认所有接口默认延迟。建议最大等待从首项入队起计，条数／字节先到即写，不能每次入队重置；控制状态触发及时 flush，提交后才确认；外部请求与重试期限匹配等待。等待期间不开写事务，队列满额背压，幂等身份不因重试变化，未提交内存不能冒充可靠结果缓存。具体数值和调度方式待确认。

获取模块可按目标配置缓存有限优质候选并打乱 pop；数据库端读取已维护的质量汇总，不在每次取代理扫描样本／随机排序全表。缓存失效、删除和证据到期须对齐；批写等待＋缓存 TTL 是数据可见的叠加延迟，不宣称即时一致。分发批次和成员可在装载时一次登记，用于后续反馈且未使用不计失败；不因此承诺每次获取完全零写入。全局退出归 lifecycle，目标证据到期与代理删除分开，规则尚待定。

状态存储补充讨论（2026-10-24）：用户提出 Proxypool 主要有来源抓取与代理测试两类任务，按发布、开始、完成更新状态，并询问未来多业务是否需要 Redis。明确区分持久业务记录与服务内存：现有业务服务持有 SQLite，运行状态可通过 API 落库，不意味着各 Worker／各进程把状态仅存在变量中。当前助手建议在既有 source_runs、check_batches 等有限业务记录保存本轮业务状态／结果完整性，以 task_id／批次 ID 关联 Crawlab 原生进程状态，不新增 Redis 作为第二份业务成功真值；此建议尚未获选型确认。

每次运行独立，不只给来源配置写一个可覆盖的 running 布尔值；周期上轮迟到不能把新一轮标完成。排队／运行等原生执行状态优先读 Crawlab，业务库只保留必要关联和业务进度，不要求完全镜像平台全部状态。成功状态与相应数据／统计同库提交；状态开始／完成的关键确认不能先放内存延后刷盘再回复成功。状态写入是短事务，按原有容量／批量原则验证，尚无实测吞吐。

其他业务保存其自己的持久输入及完成事实，不默认写进 Proxypool 数据库，也不各自只用内存。若确需跨业务的共享 URL 消费、确认与待处理回收，再评估 Redis 请求队列／Streams；Redis 是可选协调层，不替代 SQLite 业务结果。采用 Redis 仍需明确唯一状态归属、持久化／容量、未确认恢复和幂等交接，不能分别写两库就声称原子成功。依据见 [SQLite 适用场景](https://www.sqlite.org/whentouse.html)、[WAL](https://www.sqlite.org/wal.html)、[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

字段审阅状态（2026-10-24）：用户确认不保存代理来源网站，未确认首次／最近发现或抓取时间。本文 first_seen_at、last_seen_at 及依赖它们的归档／合并规则均为 M05 候选设计；具体存什么、用于什么、更新频率和删除依据统一在 M05 讨论，不能因 M03 的接口示例就提前定稿。若取消相应字段，应一并修改清理及协议，不维护无用途的时间记录。

保存代理资料、独立来源运行统计、有限近期样本和当前质量。2026-10-24 用户明确不需要代理来自哪个网站，撤回代理来源关系表和逐代理来源 URL；全局首次／最近发现时间是否保留仍待讨论，来源页面与摘要不附代理清单。每个代理／目标配置只保存最新 50 次可评分访问，超过立即淘汰旧样本；样本另有 24h 时效，不再保存 30d 全量访问明细。质量只可从仍保留的样本重算，无法任意回溯旧历史。失败更新排名，不按连续失败自动暂停或删除。长期没有发现、也没有任何成功证据时再按生命周期清理属于依赖候选字段的推荐方案。

首版不用 Redis 缓存、消息队列、通用事件平台或分库。若真实压测证明单写入事务无法满足需要，再迁 PostgreSQL；HTTP 协议和业务 ID 不随数据库改变。

## 数据表与唯一性

M03 三动作的 SQLite 候选补充：直接回调以平台 task_id 为本轮来源运行键，在 source_runs 记录 source_id／revision、绑定的 execution_id、开始／截止、最后连续提交包号、分类型计数及最终 outcome。一个任务只绑定一次执行会话，重传不刷新期限，其他会话不能混写。本轮不是代理来源映射，execution_id 不是另建通用任务队列，具体字段仍待 M05 审阅。

建议增加或复用紧凑的批次确认凭证 (task_id,batch_no UNIQUE)：规范 payload_hash、分类型记录数、固定接收／到期及必要确认；收尾保存其摘要／最终确认。无需在直接回调路径为每条发现单独保存一份端点到来源的关系，也不重复建立旧平台导入的逐条凭证；原生中转方案的 import_records 保留为另一未选路径，不同时权威写两遍。包号只在同一有效会话内递增，重复包只读已提交凭证，不重复计数。

每包数据、凭证与进度同事务；收尾时所有包已提交，最终事务只核对完整性并保存终态／必要同库下一步输入。此前“数据与成功状态同事务”不要求整轮网站抓取保持一个大事务，不能把数千条网络产出都锁在一次 BEGIN 中。批次收尾申请先等待输出确认，服务仍复核连续包及记录数，计数不是新增代理行数。

回调凭证及必要运行身份必须覆盖约定重试窗口并有硬上限，纳入整体导入／运行配额，不额外给无限额度。旧“每来源最近 20 次运行”等建议与凭证保留窗口要联合核算；如果会过早删除就需调整保留／配额或缩短承诺窗口，不能未核算直接套用。旧任务被清理后禁止迟到 start 重建，未确认的消息不能为省空间冒充成功。完整行为见 [三动作协议](../protocol.md)，尚未建表或测量。

这些是同一个应用数据库中的普通表，不是独立服务。ID 由业务生成并保持稳定；内部时间用 UTC Unix 毫秒整数，对外用 RFC3339 UTC。

| 表 | 主键／唯一约束 | 核心内容 |
| --- | --- | --- |
| sources | source_id；来源标识不复用给另一个网站 | 网站、允许代码入口、enabled、配置修订、平台周期关联、archived_at |

| proxies | proxy_id；UNIQUE(scheme, host, port) | 规范端点、first_seen_at、last_seen_at、last_any_success_at、retired_at、manual_disabled_at |

保留期内的样本与凭证不可修改，同 ID 不同内容报冲突；样本可以按数量／时间淘汰，不代表保存了所有历史。明确的管理员停用是操作开关，和质量评分分开，来源再次抓到不能清除它。

目标配置 revision 变化后为新配置预热。修改 URL、请求方式、超时、重定向、TLS、请求身份或网络范围都产生新 revision；仅改显示名称不产生。评分参数改变使用新的 policy_version 并从仍保留的样本重算，不伪造新访问。旧 revision 的质量及样本分批清掉，不维持永久历史；旧批次合法反馈只保存去重凭证并返回 obsolete_target，不重建旧统计，也不能替新配置完成预热。旧配置快照仅在仍被有效批次引用时保留，并受数量上限限制。

## 新增、停用、删除和修改测试网站

新增网站只 INSERT targets 和其 revision=1 的配置，不改 proxies 表，也不 ALTER TABLE。随后按预算选择代理进行预热，实际选中时才创建质量组合，不立即给全池生成每代理一行。

例如代理 P1 同时测试 A、B：质量表有 (P1,A,1) 和 (P1,B,1) 两行。增加 C 时先新增网站 C，测到 P1 后再增加 (P1,C,1)；A、B 的行和成绩不变。

停用 B 仅设置 enabled=0，停止新测试和新分发；已有同 revision 批次仍可反馈，有限样本正常过期。重新启用 B 时检查样本新鲜度，不从过期分数恢复满分。

删除 B 先设置 enabled=0、deleted_at，并同步停止新任务；其质量／样本后台按小批删除，其他网站与代理资料保留。迟到的 B 反馈经过原批次校验后仅保存去重凭证、返回 obsolete_target，不重建 B 的质量。批次和去重期结束、没有引用后清掉 B 的旧配置和目标行。重新添加同 URL 使用新的 target_id，不能继承已删除网站的成绩。

修改 B 的测试 URL 等语义时 current_revision 递增，新配置重新预热；旧质量和样本清理，旧批次仍按旧快照校验并作为 obsolete_target 接收。改显示名称只改 name 和 row_version，不清空评分。配置旧版本达到保留上限且仍被有效批次引用时，拒绝继续增加修订并说明容量，不擅自删除引用中的配置。

network_scope 默认 personal，只表示使用者认可的同一访问网络范围。只有同范围的测试节点与调用方才能提供这组质量证据。跨网络设备若不能视为相同环境，应为同网站登记另一个测试配置；不默认把所有 Worker 的网络表现混为一谈，也不先做每节点一套评分。

## 身份、发现与合并

首版公开来源只接受数值 IPv4／IPv6、端口 1—65535 和已支持的接入协议 http；保留 scheme 字段，增加其他协议前验证测试器及调用端兼容。生产拒绝环回、私网、链路本地、组播等非公开端点。文档中的 192.0.2.10 仅作合成示例，不能据此认定它可在生产入库。

IPv6 使用标准规范形式，构造 URI 时加方括号。相同接入协议、IP、端口才是同一代理；不同协议不强行合并。http 接入代理能够通过 CONNECT 访问 HTTPS 网站，不因此把端点改成 https。

发现结果入库顺序：在导入上下文核验运行任务及程序／来源配置 → 校验规范化 → 根据自然唯一键 upsert proxies → 记录不附端点明文的短期导入身份及进度。代理行不保存 source_id、页面 URL、抓取任务 ID 或任何来源映射，运行摘要只保留统计。全局 first_seen 取较早时间，last_seen 取较晚时间；接收迟到的发现不得倒退。整个小批次事务提交后才记录导入成功。平台暂存结果仍属于其运行任务，按有限中转策略处理，不承诺运行期间无法从平台结果看出来源。

重复发现不生成 observation，不增加成功次数，不清零失败，也不刷新 last_any_success。停用或移除来源只停止新抓取并归档来源，不修改任何已入库代理；没有代理来源映射，也不按网站删除代理。

## 访问事实、更新与事务

一次访问以开始建立连接到取得 HTTP 响应头为评价边界，latency_ms 也测量这一段。GET、禁止自动重定向、TLS 校验开启；状态码恰为 200 算成功，其他响应算该目标失败。正文解析出错或业务内容不满意不作为这次代理失败；若以后要检测正文，必须新增目标规则 revision，不能混进现有 200 语义。

| outcome | 是否计入成功率 | 说明 |
| --- | --- | --- |
| response | 是 | 有有效 HTTP 状态；200 成功，其他失败，包括 302、403、429、500 |
| proxy_error | 是，失败 | 实际尝试后的连接拒绝、隧道错误、访问超时或 TLS 错误；是此访问路径失败，不声称根因一定是代理 |
| execution_error | 否 | 缺依赖、节点本地离线、请求未真正执行、程序配置错误等可明确识别的执行问题 |
| cancelled | 否 | 调用方取消等不完整观测 |

Worker 没回结果、没有被执行的成员和上传失败不会凭空产生 observation。目标全站故障可能造成 response 失败；按现有 200 规则照实记录，不增加未经验证的自动故障归因或全池熔断。保留节点与错误类型供排查，不能把超时一概改成 execution_error 来美化成绩。

主动测试与真实使用采用相同权重。每个实际网络尝试分别记录；调用方重试两次失败后成功，应提供三个不同 observation_id，不能只上报最终成功。未反馈视为缺少证据，无法宣称统计代表全部调用的无偏成功率。

写入方法 observations.record_observations：

1. 事务外校验认证、批次成员、目标快照、时间和字段，计算规范化 payload 摘要；每包最多 500 条。
2. 开启短写事务。先查 observation_receipts 中 (producer_id, observation_id)，相同摘要为 duplicate，不再插入样本；内容冲突则整包回滚。清理已过期凭证后检查整包净增是否超过硬容量，超过则回滚并返回 CAPACITY_LIMIT。
3. 新事实写入短期凭证。当前网站 revision 的可评分结果写有限样本，并更新 last_any_success 等资料；旧配置／已删除网站只返回 obsolete_target，不建历史评分。执行异常只覆盖最近诊断。发生顺序使用首次确定的 effective_at。
4. 对每个受影响组合统一淘汰超过 24h 或不属于最新 50 条的样本，再重算一次汇总及自测时间；一包对同组合的多条反馈不反复重算。淘汰样本不删除仍有效的去重凭证。
5. 样本、淘汰、去重凭证和汇总一起提交，之后返回 accepted／duplicate。允许事务内部暂存一包新样本，但 COMMIT 后每组合最多 50 条；提交失败不返回成功。

来源导入和主动观测导入还要在同一事务写 import_records；不能先推进平台分页游标再保存业务数据。[SQLite UPSERT](https://www.sqlite.org/lang_upsert.html) 只解决唯一冲突；业务冲突比较与事务边界仍需我们实现。

2026-10-26状态设计补充：用户要求同时考虑代理获取接口。测试成员状态不代表代理可调用状态；当前质量、自测安排、分发反馈身份按职责区分，复用同一按目标质量汇总及有限观测。具体建议、真实反馈与自测占用关系、缓存失效和资源边界唯一维护在 [共同状态](../protocol.md#自测代理获取与真实反馈的共同状态2026-10-26设计补充)，均未实现；不把任务pending当全局不可调用。

## 质量计算与分发

默认评分策略标识 wilson-24h-50-v1，时间窗口 (now−24h, now]；在此范围内按 (effective_at DESC, producer_id DESC, observation_id DESC) 保留最新 50 条有效观测。相同评价时间用稳定键排序。超过条数的旧样本在写入事务中直接淘汰，不保留额外全量历史。成功率用浮点比例 0—1，score 取 0—100，计算用完整精度，展示保留两位。

设 s 为成功数，n 为有效样本数，p=s/n，z=1.96。标准 Wilson 下界为：

```text
score = 100 * (p + z²/(2n) - z * sqrt(p*(1-p)/n + z²/(4n²))) / (1 + z²/n)
```

这是引用的现成算法；24h、50 和保留策略是本项目的可调整默认值，没有实测证明它们最优。n=0 时 success_rate 和 score 均为 null，表示未知；n>0 且全部失败时 score=0，表示有失败证据。两者不能混同。

| 成功／样本 | 表面成功率 | score 约值 |
| --- | --- | --- |
| 1／1 | 100% | 20.65 |
| 10／10 | 100% | 72.25 |
| 49／50 | 98% | 89.50 |
| 45／50 | 90% | 78.64 |
| 0／10 | 0% | 0 |

只在同一目标 revision 下比较。分发排序：score 从高到低 → 成功请求耗时EWMA从低到高（缺失最后）→ last_allocated_at 从早到晚 → proxy_id。速度只在稳定性分数相同时参与；不另做质量／速度加权总分。返回一批不同端点，不承诺不同公网 IP，也不承诺跨批互斥占用。

min_score 由调用请求决定，缺省为 0；不会因为分数低而全局暂停代理。需要较稳候选的调用程序可显式传 50 或更高，达不到数量返回部分或空列表。它是该次申请的筛选条件，不能写成代理状态。未测试和证据全部过期的组合先走自测，不自动掺入正常分发。接口总是返回样本量和发生时间，score 不等于成功率。

24h 后没有新访问，旧成绩应自然过期，即便没有新写入。汇总保存 valid_until=所选最早样本的 effective_at+24h；到时重算并清理过期样本。后台每分钟小批刷新，分发查询不得直接使用已到期的旧分数：优先补算相关候选，未能补算的本次不选并返回 quality_refresh_pending；不能把过期高分长期当有效。客户端小幅时钟超前按上述 effective_at 规则处理，不另保留未来样本。

## 主动测试更新

2026-10-26确认补充：用户明确测试闭环：M04测试系统从M05取得本轮需要测试的代理＋目标组合，M05在返回前持久标记为待测试，再由M04发布到Crawlab；Worker处理后直接回传M05，M05更新状态和结果。下一轮重新向M05获取需要测试的内容；Worker不自行重新安排或重跑测试任务。选测规则必须考虑已安排状态，避免重复发布。下述时间／分组和预算仍是建议；同事务选取及占用、next_check_at等候选字段、无反馈到期及迟到处理以 [主动测试协议](../protocol.md#主动测试任务) 为当前讨论依据，不以旧预算自动定稿。

testing.select_checks 根据真实观测选择，而不是 last_allocated_at。默认参数如下，均为建议，可按目标覆盖：

| 情况 | 建议处理 |
| --- | --- |
| 最近 5min 内有成功观测，且之后没有失败 | 本轮跳过重复自测；自测和实际使用都可提供成功证据 |
| 更新前 score≥60、最新一次有效观测失败 | 距这次失败至少 1min 后优先复测；不暂停分发，真实失败已经降低评分 |
| 新代理／新目标配置，尚无证据 | 进入预热候选 |
| 正常有证据 | 距最近有效观测 30min 后进入常规自测候选 |
| 分数较低或最近均失败 | 仍每 30min 有复测机会，避免每分钟反复消耗；调用反馈随时可以更新 |
| 已有相同组合在途 | 不重复安排，平台任务异常后释放业务成员关联；未执行不扣分 |

失败后优先复测标记根据写入前的 score 生成，随后被更新的成功／失败取代。三个候选组（失败复核、预热、常规）轮流各取一个，组内按到期时间最早优先，空组跳过；避免新来源或失败复测长期饿死其他组。不引入独立队列服务。

初始预算建议每个目标每轮最多 20 个、业务每分钟最多发布 60 次测试，单任务并发 5，首版同时最多一个主动测试任务。预算是发布端控制量，不能宣称等同远程节点精确每秒限流。抓取来源任务不受“主动测试任务只能一个”的限制。实际预热时长取决于代理和目标规模，不能承诺加网站后立刻有一批高分代理。

每目标仅按需求创建质量记录，测试输入按预算生成，不预先物化所有代理×所有目标的笛卡尔积。

## 失效、归档与删除

质量过期不删除代理；分发到期不算失败；来源停用不删除代理；单个网站失败不删其他网站的成绩。禁止按连续失败次数或单次状态执行自动暂停／删除。

| 数据 | 推荐保留及处理 |
| --- | --- |
| 近期有效样本 | 每组合最多 50 条，同时限制 24h；条数或时间任一超限即淘汰；新反馈发生于最近 24h，超期明确拒绝，不凭空记失败 |
| observation_receipts | expires_at 固定为所属批次 use_before／execute_before+48h，默认允许反馈 24h；仅保存身份、摘要、时间及关联，晚到不滚动延长期限；受总量上限约束 |
| 分发及测试批次、成员、请求幂等结果 | 使用／执行截止后保留 48h，与凭证同一固定到期边界；到期时样本本身也应超过 24h，先清子记录再清凭证及批次，不无限互相延长 |
| 来源页面明细 | 每来源最近 3 次已完成运行，且不超过 7d；更旧页面可删，摘要独立；未完成运行受全局配额限制 |
| 来源运行摘要 | 每来源最近 20 次已完成运行；总运行行有上限，异常未完成也不能无限追加 |
| import_records | 未完成导入阶段保存有限凭证；完成且核对数量后保留运行完成摘要，删除逐条导入凭证；自动导入不重新扫描已完成／已淘汰的旧任务 |
| 目标旧 revision | 仅保留当前及仍被有效批次引用的配置，每目标最多 5 个；旧质量和样本不长期保留 |
| 代理归档 | last_seen_at 和 last_any_success_at 都早于 now−30d，且没有在途测试或仍可使用的分发成员，设置 retired_at |
| 代理物理删除 | 归档再满 30d，期间无新发现／成功，所有相关事实和批次引用都已过保留期，才分批删除质量和代理行 |
| 人工禁用代理 | 不参与新分发及自测；再次发现不清除此标记；管理员可显式恢复 |

从未成功的代理以 first_seen_at 作为成功时间为空时的清理比较基准。任何目标有真实成功，都能刷新 last_any_success_at，不能因未再出现在公开列表就删掉仍在使用的代理。自动归档后再次发现可清除 retired_at 并重新测试；旧证据仍遵守 24h 窗口，不重新获得历史满分。迟到反馈只有经有效批次和时间验证的成功才可更新／撤销自动归档，不能撤销人工禁用。

持续被来源列出、但一直失败的代理不会因上述时效规则自动删除。达到端点硬上限时仍更新已有端点和反馈，拒绝新增并报告容量；不静默淘汰好代理、不停止全部来源抓取。人工移除先归档并保留有效批次引用，避免破坏反馈处理。

样本条数在每个写入事务中修剪，不等待每日任务；每分钟小批清理时间到期样本和凭证；每日低负载做无引用配置、批次及端点维护，每事务最多删除 1000 行。清理先删到期子记录再删无引用父记录，每一步重查引用；不能因为删除网站级联清空整个代理。SQLite 删除后页通常供后续复用，文件未缩小不等于未清理；不在每次删除后 VACUUM。

## 数量硬上限与满容量处理

所有数值是可配置的推荐起点，用户确认的是必须有上限，不是已经确认这些具体数值。限制按提交后的行数执行，并通过单写事务入口串行检查，不能只在午夜清理时检查。

运行时配额使用固定允许项的 storage_counters(quota_name PRIMARY KEY,used_count) 小表，插入／删除的实际净增量与业务行在同一事务更新，冲突跳过不计新增，回滚也回滚计数。启动或维护时核验实际行数，发现不一致先修正再接纳写入；不在每个反馈包上 COUNT 全部百万级样本或凭证。它只服务当前配额，不建设额外计量平台。

| 内容 | 推荐硬上限 | 达到后处理 |
| --- | --- | --- |
| 代理端点 | 100000 | 继续更新已有端点，新增报容量，不清空旧评分 |
| 来源配置 | 50 行，含归档 | 清理无引用归档后才能新增 |
| 未删除网站 | 20 个，含停用 | 新增报 TARGET_LIMIT，用户可调整限额或移除网站 |
| 网站行总数 | 1000，含等待清理的删除标记 | 清掉无引用已删除行；满时拒绝新增，不能无限累积墓碑 |
| 每网站配置版本 | 5 个 | 优先清无引用旧版本，仍满则拒绝新修订 |
| 代理／网站／revision 质量组合 | 50000 行，含在清理中的旧版本 | 先清过期、无在途引用组合；仍满则不安排新组合，已有反馈正常处理 |
| 有效样本 | 每组合 50 条，全库最多 2500000 条 | 保留该组合较新的样本，同事务淘汰旧样本；不额外保存全量历史 |
| observation_receipts | 2000000 条 | 清过期后仍满则拒绝净新增并返回可见 CAPACITY_LIMIT；重复已存在的反馈仍可确认 |
| 测试＋分发批次 | 合计 250000 个 | 先清过期无引用批次；满则拒绝新批次，已有反馈仍受最终写入上限约束 |
| 测试＋分发成员 | 合计 2500000 行 | 分发／发布前为整批预留，放不下则拒绝该批；不先发出再丢输入 |
| 来源运行 | 合计 2000 行 | 保留每来源最近 20 次摘要并清无引用旧运行；未完成占满则停止接纳新运行并告警 |
| 来源页面 | 合计 100000 行，每次运行最多 1000 页 | 清旧完成运行的页面；单轮超额在执行输入中限制，不能继续无界保存 |
| 未完成导入凭证 | 合计 200000 行 | 先完成／清理可清任务；仍满则停止新导入包，不 ACK 后丢数据 |

不建立代理来源关系表，移除原先代理数×来源数的关系行预算；target_revisions 最多为目标行上限×每网站版本上限。JSON 配置／摘要单条最多 8KiB、URL 最多 2048 字符，字段与列表都校验长度；只限行数却允许单行无限长不能算容量控制。

达到去重凭证上限时，不能提前删有效凭证又承诺反馈期内重试不重计；明确采用背压而非这个矛盾承诺。容量是固定空间与可持续流入速率之间的取舍，可以配置扩大，不能暗中放开。服务启动及配置下调先验证现有占用；低于当前占用的限额修改返回冲突，不为满足新限额静默删除仍有效的数据。

这里的有效引用是仍可执行、使用、反馈或导入的业务引用，不是“数据库里还存在一行”。凭证与批次不能因互相有外键而无限延长保留；期限已结束且无近期样本等引用时，按先子后父清掉。

这些上限针对 Proxypool 业务库。Crawlab 原生结果与任务日志是另一份存储，也必须有平台侧容量、有限保留与清理方案；只限制 SQLite 不能声称整个集群有上限。后续原生接入验收需核对所选版本的安全清理能力，并保护未导入结果；能力未验证前不假定平台自动完成，不在本轮执行清理或另建存储平台。

数据库主文件额外建议上限 4GiB，按实际 page_size 设置 max_page_count，4KiB 页时为 1048576 页。该设置只限制主文件，WAL／SHM／备份另有空间需求，不能声称整个目录固定 4GiB；参见 [SQLite max_page_count](https://www.sqlite.org/pragma.html#pragma_max_page_count)。主文件满或提交失败整包回滚并返回错误。容量压力和性能目标详见下节，不把 SQLite 的理论极限作为应用配额。

## 性能目标、流入速度与空间预算

SQLite 在本地短事务和索引查询的前提下适合本方案，但没有一个适用于任意 schema、磁盘和同步策略的固定 QPS。[官方选型说明](https://www.sqlite.org/whentouse.html) 明确单文件只允许一个并行写事务；[WAL](https://www.sqlite.org/wal.html) 允许读写并行。synchronous=FULL 时提交要同步磁盘，合批减少提交次数。容量配额是本项目选择，不是 SQLite 到这个条数就变慢的界线，也不是已经跑出的性能。

分发接口会写 allocations 和 members，不能算成纯读取；一次新观测还会写凭证、样本、修剪、索引及质量。一条观测不是一条 SQL。初始验收工作量建议如下，各预算共同约束，不能分别取最大后当作同时承诺：

| 工作 | 建议目标与入口预算 | 计量方式 |
| --- | --- | --- |
| 新访问结果 | 合计持续 5 条/s，可容纳 20 条/s 持续 10s 的短峰；初始突发桶 500 条 | 自测、调用、旧配置确认和执行异常的净新增凭证全部计入；不是 5 次 HTTP 请求 |
| 新批次 | 分发＋测试合计持续 1 个/s，短突发桶 50 个 | 一次申请不论返回多少代理都占一个批次，重传已有批次不重复占用 |
| 新批次成员 | 合计持续 10 个/s，短突发桶 1000 个 | 未实际使用的已分发成员也占容量；不能只按实际访问数估计 |
| 查询列表／概览 | 验证 20 个/s 的索引分页读取 | 是压测目标，不承诺任意全表统计都在此速率内 |
| 来源导入 | 每分钟最多导入 2000 条业务记录，每包≤500 | 另计，不混入观测结果速率；受代理、关系及导入凭证容量控制 |

推荐复用现成限流组件或业务入口的小型令牌桶实现上述预算，不新建限流服务。实际并发和速率在隔离压测后确认。60 次/min 的自测发布量仅是总 5 条/s 新结果预算中的一部分，不能每个 Worker 各自获得一份全局额度；它也不保证全部待测组合在 30min 内测完，30min 是进入候选的条件。

容量关系为：凭证存量≈净新增结果速率×固定保留时间；成员存量≈新成员速率×成员保留时间。首版改为反馈最长 24h、凭证／批次在使用或执行截止后固定保留 48h，替代此前 7d 反馈／8d 保留建议。原因是后者在 5 条/s 时需约 345.6 万条凭证，超过旧 100 万配额；若确需一周离线补报，应先重新核算并确认更大容量，不能只改时间参数。

| 持续新结果速率 | 每天条数 | 保留 48h 的基础凭证量 |
| --- | --- | --- |
| 1 条/s | 86400 | 172800 |
| 5 条/s | 432000 | 864000 |
| 10 条/s | 864000 | 1728000 |

固定到期从批次截止起算而非接收时滚动：分发默认 5min、测试默认 10min，因此最坏要再计这段批次有效时间和突发余量。5 条/s、最长额外 10min、突发 500 条，约 867500 条凭证，低于 200 万上限；1 个/s 新批次加突发与 10min，约 173450 个，低于 25 万；10 个/s 新成员约 1735000 个，低于 250 万。额度异常或历史重放仍由硬上限兜底，不把估算当精确实测。

工作规模示例：1000 个代理×5 个网站全部有样本时为 5000 组合、最多 25 万样本；2000×10 为 2 万组合、100 万样本；5000×10 达到 5 万组合、250 万样本硬上限。100000 代理端点上限是可收录端点量，不表示全部端点都会针对所有网站测试。

空间只做预算：若样本含索引按 512B/条估、紧凑凭证按 256B/条估、成员按 384B/条估、批次按 1KiB/条估，满额分别约 1.19GiB、0.48GiB、0.89GiB、0.24GiB，合计约 2.80GiB，尚有页面、运行、代理资料和空闲页开销；不再预算代理来源关系。以上单价是设计假设，schema 未实现，不能承诺各配额全部能同时填满 4GiB。实际用 [dbstat](https://www.sqlite.org/dbstat.html)／sqlite3_analyzer 测表与索引；dbstat 是否可用取决于编译选项。

每类行数配额达到 80% 显示预警；达到 90% 停止会扩大该类存量的新分发／新测试／新配置，已有反馈优先处理但仍受最终硬上限。主库空间以 (page_count−freelist_count)×page_size 观察已使用页，避免已删除但可复用页导致误判：3GiB 预警，3.5GiB 停止新增来源端点／网站／批次并加快合规清理，4GiB 为主文件兜底。长时间占用过高或写延迟恶化时先检查索引、事务、清理和保留设置，不直接扩大所有配额。

WAL 另设 256MiB 预警、512MiB 暂停普通业务写入并诊断 checkpoint／长读事务；维护用 checkpoint 仍允许。这是应用观察阈值，可因在途事务短暂越过，不是 WAL 文件的内核硬配额。journal_size_limit 主要控制重置后保留大小，不能保证活跃 WAL 永不超限，参见 [官方说明](https://www.sqlite.org/pragma.html#pragma_journal_size_limit)。不手动删 WAL，不在每个请求中强制 TRUNCATE，不为缩文件在请求路径执行 VACUUM；维护和备份另预留临时空间，不能只留 4GiB 磁盘。

## 持续测试与 SQLite 负载判断

2026-10-24 用户认可由常驻 API 接收 Worker 反馈的方向，继而询问持续测试是否适合 SQLite，并明确暂不确定预期吞吐，希望先了解一般适用负载。因此不能把此前 5 条/s 推荐预算当用户需求或 SQLite 能力上限，也不据此自行改成某个高吞吐目标。

适用负载画像：数据库在单机本地、查询有索引、读多或读写混合、少量集中写入口、写事务短、可合批。持续写本身不构成不适用；关键是写锁占用时间、提交次数、行／索引修改量和磁盘同步。多个 Worker 经 API 访问不等于多个 Worker 直接写 SQLite 文件。WAL 可读写并行，但仍只有一个同时写入事务，见 [WAL 并发说明](https://www.sqlite.org/wal.html#concurrency) 和 [官方选型](https://www.sqlite.org/whentouse.html)。

不利负载：多个写服务要求同时持续写且不能排队、长期大写事务、频繁复杂全表扫描／统计、多个设备直接共享数据库文件，或在持续混合写入下要求很低尾延迟。此时应比较 PostgreSQL 等服务端数据库，不因“用了异步”就认为写锁限制消失。官方 FAQ 的 [合并事务说明](https://www.sqlite.org/faq.html#q19) 支持摊薄提交成本，但其中历史插入跑分不是我们业务性能保证。

仅作计算例：1000 条结果/s，若每条各自提交，是 1000 次事务/s；若凑足 100 条一事务，是约 10 次事务/s，仍要处理 1000 条记录与其全部索引／质量修改，不是工作量降成 10 条。多个生产者按等待时间提前发送小包时，实际事务数还会增加，不能把全局结果速率简单除以最大包量当实测提交速率。

当前输入粒度以用户 2026-10-25 新设想为准：先提交有限测试批次、小任务和固定成员清单，再按同目标配置切小批发布原生任务；例如 100 项一个平台任务，不再每个代理启动一个原生任务。Worker 读取本小批快照，逐项成功或失败都生成结果并分包回调 M05；有界队列可合并写事务，不能为等大批全部结束而无限缓冲，每包确认须等待真实提交。

建议在同一短事务内验证成员／原生任务身份、去重、写入有效观测与质量汇总、将未终结成员转终态，并仅在首次终结时递减批次未完成数；减至零时同事务结算批次。无有效网络观测的执行错误／超期只更新任务成员，不降低代理评分。重复结果不重复计分／计数；超期与结果的竞态由统一写入口和条件更新裁定，终态不被迟到反馈静默回退。迟到结果能否另作观测及具体窗口待 M05 确认。

每项成员及所属小任务都在发布前存在；发布失败、平台异常和无回调不能使成员从预期总数消失，原生 task_id 关联小任务。M04 在事务外调用 Crawlab；结果不明确先核对关联，避免盲目重发。已有维护循环按截止索引有界结算，不新增常驻恢复服务。小任务及批次头只存有限计数，成员复用已有 check_members；结果与状态共事务，不为每次轮询写一条历史。具体索引、保留量与字段仍留 M05 审阅。

持续流量同时决定保留成本。示例 100 条/s 为每天 864 万条；若每条凭证完整保留 48h，基础约 1728 万条，已超过现草案 200 万凭证额度。这说明流入／保留／容量必须一起改，不是 SQLite 在 100 条/s 必然写不动，也不能只提高限流而保留旧容量承诺。上述示例不是用户目标。待字段与状态方案确认后，压测应包含真实事务、查询、分发写入、清理和 checkpoint，观察 P95／P99、写锁等待、WAL、积压与磁盘增长；没有授权前不运行测试。

## 批量写入与读取

用户已认可缓存队列积累后写入，并要求整套流程适合 SQLite。候选在 M05 内用有界写入队列和一个写入执行入口，将多个允许的小包按条数／字节／最大等待时间合批；无须为此增加独立服务或 Redis。Worker 可减少 HTTP 次数而小包提交，但生产者与服务端应共用总等待预算，不在两端各等完整合批周期。原先“100 条或 1s”为未确认示例，具体阈值、队列上限和延迟预算均配置化。生产者在确认前保留稳定 ID 和内容；内存队列不是持久任务队列，不能将未确认内容宣称已保存。

服务在事务外做格式校验／规范化，进入队列后由单个写入入口执行短事务；与数据库当前事实有关的身份、修订、停用、配额和幂等检查在事务内复核。一个 HTTP 包仍保持全包原子语义；合并多个包时可复用 SQLite SAVEPOINT 保持各包隔离，但只有最外层 COMMIT 成功后，才逐包完成等待的请求并返回 accepted／duplicate。业务冲突不能污染其他包；数据库级故障使整次提交失败时不能提前确认任何包。不在业务方法中各自嵌套 BEGIN；实现若先只串行处理已合批包也可行，跨包合并收益须验证后决定。

去重、写样本、修剪、质量及批次进度一起更新，同一事务对每个受影响组合只汇总一次。仍为每次独立访问保存必要短期凭证，不把一百次访问合并成一个事实。单包上限、单事务总记录／字节和受影响组合数必须协调；超出约定原子包上限时在写前拒绝并要求拆包，不擅自部分提交。管理员停用／删除、开始授权和完成确认可触发及时 flush，但仍走同一写入口；不绕过队列用另一写连接抢锁，不让普通结果长期饿死。

队列同时限制请求数、记录数、总字节及等待时间，阈值先到即 flush，空闲时也不能无限等待凑满。满额或预计无法在请求期限内处理时，入队前返回明确可重试错误及 Retry-After，暂停扩大新测试／抓取预算，不无限堆内存。请求超时不等于撤销已提交事务；不确认提交结果时使用原 ID 重传并查已处理凭证，不能换 ID 重试。开始／完成写入必须等待提交确认，Worker 在本批输出确认前不发“全部完成”。服务重启依持久状态及未确认重传恢复；若 Worker 也同时丢失内存，缺结果仍是缺证据，按任务恢复规则处理，不虚构成功或代理失败。

取代理主要读取已有索引的质量表，不扫描全部访问样本；明细只在更新或到期重算时读取每组合最多 50 条。首版不另加代理排名读取缓存，避免过期分数与停用状态不同步；这与写入合批队列用途不同。短期诊断覆盖更新、过期清理和来源健康摘要同样按小批操作。

## 端到端 SQLite 流程约束

本节是按用户要求形成的具体建议，确认的是“流程适配 SQLite＋允许缓存合批”的方向，字段、数值和实现细节未因此全部定稿。

| 环节 | 针对 SQLite 的流程安排 |
| --- | --- |
| 周期来源抓取 | Crawlab 运行与状态不移入 SQLite；业务只保留必要本轮关联。网站脚本抓取解析后有限批量输出端点和独立统计，业务结果走选定的单一确认路径，不逐代理更新来源关系 |
| 选测与建批次 | 通过索引有限读取到期候选，在短写事务复核目标／配置／在途及配额，保存一批输入与必要快照，提交后才调用 Crawlab；不在数据库锁内联网 |
| Worker 测试 | 一次取得该批代理与目标配置，内存中执行网络请求，不每测一个代理查询一次 SQLite。开始状态提交后执行；结果有限缓冲／回传，保持每次真实尝试身份 |
| 结果写入 | 公共反馈 → 有界队列 → 单写入口。校验、去重、有限样本修剪、受影响质量及批次进度同事务处理，外层提交后才确认；不逐条 fsync／全库重算 |
| 测试批次完成 | 按固定成员逐项结算；首次成员终结与批次进度同事务，无未终结成员后批次结束，不需要某 Worker 发送整批 finish。发布失败／无反馈由有界维护归为执行异常或超期，不能虚构代理失败；正常返回失败测试也算成员完成 |
| 代理调用与反馈 | 排名走已有质量索引，检查有效性与停用；新分发要保存批次／成员，是写操作，也走统一入口，提交后才能把批次交调用方；真实访问反馈沿相同结果写入路径 |
| 评分及到期 | 每次事务只更新受影响组合；到期刷新按 valid_until 索引小批处理，不能每次取代理扫描样本或定时重算全池。若改成延后汇总，须先明确旧分数可见性，不能默默异步确认 |
| 状态与开关 | 保存每轮／批次必要状态，关键转换及时提交；用当前执行关联／版本和条件更新防重复迟到，不给每个网络细节都独立写状态。平台同步在 SQLite 事务外执行 |
| 页面展示及查询 | 有索引分页、短读事务，使用已经维护的统计；不频繁全表 COUNT／聚合、不长持游标和读事务阻碍 checkpoint |
| 清理与维护 | 过期凭证、样本、旧运行和归档按索引／数量小批，与结果写入共用入口，避免一次大 DELETE；checkpoint 观察 WAL 和长读，VACUUM／全量扫描不在请求路径 |

写入队列、数据库提交和在途网络请求都有上限，缓存不能解决长期流入高于处理能力；通过拒绝／限速并减少新发布使负载回落，不先吞下无限工作。WAL、同步／外键和实际查询计划按本稿现有方案核验，执行器不得把阻塞数据库工作直接占住 HTTP 事件循环；具体驱动和后台执行方式留实现阶段选择，不自写数据库驱动。

验证应覆盖全链路而非纯 INSERT：测试回传与分发、清理同时运行，观察提交延迟、锁等待、队列深度／最老等待、CPU／内存、WAL 和容量；还要验证多包合并时某包冲突、COMMIT 失败、客户端超时重传、关停排空和异常中断。SQL 原子性依据 [事务](https://www.sqlite.org/lang_transaction.html)，读写边界依据 [WAL](https://www.sqlite.org/wal.html)；这些不是已完成实现或压测。

## 索引、持久性与规模边界

必备索引：proxies 的自然唯一键；observations(proxy_id,target_id,revision,effective_at DESC) 及 effective_at 清理索引；observation_receipts 的联合唯一键及 expires_at；quality(target_id,revision,score DESC)、quality(valid_until)；批次的 caller/request 唯一键及过期时间；各成员的 proxy_id 外键索引；source_pages 与 import_records 的任务键。

首版一个业务服务进程、所有写操作使用同一个进程内写事务入口。只在数据库操作期间持有写锁，网络调用、Crawlab 分页、JSON 校验和文件处理都在事务外。单批上限 500 条，每个受影响组合最多读 50 条；大包拆分后每包分别确认。不引入先 ACK 再写内存队列的可靠性缺口。

建议配置 WAL、synchronous=FULL、foreign_keys=ON、busy_timeout=5000ms，并实际读回验证；启用默认自动 checkpoint，避免长期持有读事务。[FULL 的持久性含义](https://www.sqlite.org/pragma.html#pragma_synchronous) 依赖正常工作的文件系统和磁盘同步语义；不能承诺抵御硬件故障。[外键必须逐连接开启](https://www.sqlite.org/foreignkeys.html)。实现时核对实际 sqlite3 运行库，而不是只看 Python 版本；[官方 WAL 文档](https://www.sqlite.org/wal.html#walresetbug) 说明 WAL-reset 问题在 3.51.3 及后续版本修复，另有指定旧分支回补。选择届时受支持且已修复的运行库，不把未经核验的系统内置版本当可用。

数据库目录未来使用 /srv/persistent/data/proxypool/，SQLite 文件及其 WAL／SHM 处于同一本地持久目录，不挂 NFS/SMB，也不放在 Worker 共享卷。在线备份使用 [SQLite Backup API](https://www.sqlite.org/backup.html)，不单独复制活跃的主文件冒充一致备份。这里约定方式，不表示已启动备份建设或部署。

样本规模按组合数估算而不是把每日访问量乘以 30 天：1000 个有质量记录的组合最多 50000 个有效样本；再多访问也只替换旧样本。全库由 50000 组合×50 样本限制为 250 万条，另计有独立硬上限的短期凭证与批次；这些上限不表示所有配额一定能在额外主文件空间限制内同时占满。字段、索引、WAL、空闲页和备份的实际字节数须用真实 schema 测量。

后续获准实现后，在同等 SSD 环境以数据配额 10%／50%／80% 三档做混合压测：持续目标负载至少 30min，同时执行来源导入、反馈写入、样本淘汰、分发及清理，并额外验证 20 条/s 的 10s 短峰和 500 条最大包。分别覆盖结果集中于少数组合与分散于多个组合，不能只测纯 INSERT。

建议验收指标：普通分页读取 P95<100ms；分发与≤100 条反馈包 P95<200ms；500 条最大包单独观察并以 P95<1s 为目标；测量不含生产者凑批的最多 1s 等待。记录 P99、写锁等待、CPU／内存、未处理 SQLITE_BUSY、WAL 峰值及 checkpoint 恢复。还要验证重启重传、满配额、磁盘满回滚、网站删除及修改版本时反馈仍正确。所有数值均是工程目标，尚未实测。

若达到建议工作量且指标稳定，保持当前 SQLite。若短事务、索引和清理优化后仍不达标，或确定要多个业务服务器实例同时写同库，再提出迁 PostgreSQL；增加远程抓取 Worker 本身不触发换库，不能只看行数就宣布 SQLite 不够用。
