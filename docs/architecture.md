# 当前架构

2026-10-29 本地实现基线。进程分开部署不等于每个业务模块都必须单独占一个常驻容器。

| 模块 | 代码／运行组件 | 责任 |
| --- | --- | --- |
| M01 | 既有 Crawlab Master＋专用 Mongo | 程序、源码同步、节点、执行状态与日志；不保存代理业务真相 |
| M02 | 既有通用 Crawlab Worker＋独立任务环境 | 接任务、启动程序；每节点任务槽与 Docker 配额沿用设备配置 |
| M03 | `apps/proxypool/publishers.py` 的 capture | 固定周期轮前清理、发布启用来源，成功发布后记录 Task ID；立即结束，不等抓取完成 |
| M04 | 同文件的 tests | 双时间规则选测、按目标切块、串行发布、记录安排时间 |
| M05 | `apps/proxypool/service/` | 唯一 SQLite 业务写入口、统一反馈、选测读取、候选获取、配置与统计 |
| M06 | `apps/proxypool/web/` | M05 同源单页，不另启 Node 服务；详细任务日志跳转 Crawlab |
| M07 | `integrations/crawlab/client.py` | 原生 API 薄适配，不维护另一套任务状态机 |
| M08 | 后续其他业务应用 | 使用独立 Crawlab 程序／业务服务；不改造为通用 Proxypool 插件 |

首版 M03／M04 与 M05 同一个 Python 进程，但代码责任分开。一个实例、一个写线程、有界内存队列、两个配置化读线程；不启多 Uvicorn Worker。这样不引入跨进程队列、Redis或业务 Mongo。Worker 不挂载 SQLite，结果直接 HTTP 回传 M05，确认 COMMIT 后才认为业务交付成功。

抓取流：固定周期 → 本轮开始快照清理 → 发布来源原生任务 → Scrapy 下载／解析 → 标准端点列表与来源摘要 → M05 去重入库并更新最近健康。HTML 由 Scrapy 在任务进程内处理，不默认保存全部网页。

测试流：M04 按目标读取端点 LEFT JOIN 质量 → 判断双时间 → 每个 Task 测一块（默认 100） → aiohttp 有界并发 → M05 统一反馈与计分。程序实际请求每成员一次；只有回调传输有限重试。

使用流：调用方按 target_id 获取 → 小型内存候选队列 pop → 实际访问 → 同一个反馈接口。获取不写库、不登记领取身份，未使用／未回传不算失败。候选缓存期间分数可能滞后到 TTL，已接受这种取舍。

来源扩展：每网站一个 Scrapy 类，可以处理分页。内置三个入口；自定义脚本经本地审阅测试、显式注册后由 Crawlab 同步到执行工作区。不扫描目录、不导入未注册脚本。新脚本不增加依赖时只更新原生源码，不改节点运行环境。完整程序交付见 integrations/crawlab/program.py；节点环境由集群侧准备，业务服务不管理Worker。

## 资源与上限

以下是可调整默认值／部署预算，不是服务器实测：

| 项目 | 默认值与满额行为 |
| --- | --- |
| M05 容器 | 0.5 CPU、512 MiB、64 PID；单进程，SQLite 写连接页缓存约16 MiB |
| 写队列 | 最多10000条／128个排队请求；另有一个处理批次；满时503，发送侧有限重传 |
| 数据合批 | 第一条起1秒或1000条提交；配置／安排／清理及时提交；可改为10秒但同步回调也会相应等待 |
| 单请求 | 1000条、256 KiB；超出413，任务程序同时按条数及实际JSON字节拆包 |
| 去重内存 | 60秒、最多20000 ID；不落库，重启或容量驱逐后不保证极晚重传只计一次 |
| 目标／来源 | 最多32／64；达到后409，按实际家庭设备调小 |
| 获取缓存 | 每目标100条、TTL60秒；空／过期才重新读排名 |
| 代理池 | 100000软上限；抓取发布前只清理当时超出的数量，不承诺本轮结束不超量 |
| 测试发布 | 每60秒最多1个100代理任务，Worker内部并发20、每请求10秒；任务槽由Crawlab限制，节点私有并发上限再次约束请求数；本业务pending＋running默认最多8个，满额跳过本轮 |
| 来源执行 | 每网站120秒、最多10000条／50页；无无限分页和无限原始HTML留存 |
| 日志 | M05 Docker local日志10 MiB×3；Worker／平台沿用既有配额与保留策略 |

发布数量是业务工作预算，不是 Crawlab 全局排队上限。默认每小时最多安排约6000次测试；10万代理一个目标全池覆盖至少16.7小时，32目标至少533小时（均未计任务耗时和失败）；5分钟最小间隔不是全池5分钟刷新承诺。实际完成量还受网站耗时、来源任务和Worker槽位影响。提高代理池容量不会自动提高测试吞吐，需一起调整任务预算、节点数和请求并发，避免积压超过测试timeout。不要仅按CPU核数推测网络任务吞吐。

SQLite 不保存逐次历史表，质量行上界约“当前代理数×已接入目标数”，按需生成。软池上限允许暂时超量，磁盘仍需保留WAL、索引与一次事务的空间；不是硬字节配额。排名使用索引，选测按一个目标流式扫描，轮前淘汰按当前质量汇总。当前实测见验证记录。

Crawlab 0.6核心源码已有任务／统计约30天清理与日志TTL机制，但不等于所有Artifact和工作区物理文件都已验证有界；本次没有改现有平台配置。服务器部署时观察实际持久卷增长，不再创建另一套业务任务历史库。
