# 家庭服务器部署设计约束

本文件将服务器搭建规范映射到爬虫项目。2026-10-25 用户授权先部署 Crawlab Master、专用 MongoDB 和一个 Worker；明确由用户执行服务器部署，本地助手可只读核验、准备配置和命令并按输出验收，不代为写文件、拉取镜像、启停容器或修改网络／权限。2026-10-29业务已完成本地实现，正式部署步骤见deploy/proxypool/README.md；本地没有启动实际采集／公网代理测试或迁移旧生产服务。用户已提供Master／MongoDB健康、Worker上线、Master禁用执行、一次SDK任务及API结果读取通过的证据；不因此认定跨设备访问、实际资源或业务SQLite已验收。

## 规范来源

本轮具体体验配置和用户操作顺序见 [部署包](../deploy/crawlab/README.md)。已准备 Compose、空库用户初始化和只准备文件的 prepare.sh，固定社区版 0.6.3 及 MongoDB 7.0.45-jammy 的 amd64 digest；本地检查不能替代用户在服务器执行 config -q、启动兼容性、登录及节点验证。数据库和 Master 先启动，禁用 Master 执行并修改密码后再启一任务槽 Worker；不自动运行业务任务。

来源为 [home-server-ops 的 facts.yaml](https://github.com/LorewalkerAlex/home-server-ops/blob/main/facts.yaml) 中的 directories、conventions.network 和 conventions.deployment；本轮参考其 2026-10-23 记录。服务器任务状态仍以该仓库 progress.md 为准。

服务器规范不代表各项措施已在本项目实施。部署时按任务范围核对现行配置，不把历史快照当作实时检查，也不复制整份服务器事实到本仓库。

运维仓库仅维护四份公开知识文档的约定适用于运维仓库；本代码仓库按模块保留必要设计文档与未来部署声明，不在其中重复建立服务器资产清单。

## 目录与数据

| 用途 | 沿用约定 | 本项目处理方式 |
| --- | --- | --- |
| 服务部署 | `/srv/apps/<service>/` | 后续按实际组件保存 Compose 与服务 README |
| 业务持久数据 | `/srv/persistent/data/<service>/` | 数据库、原始产物与必要处理状态分别明确挂载 |
| 私密配置 | `/srv/persistent/secrets/<service>/` | 环境文件或受支持的文件注入；Git 只保存变量名和示例 |
| Docker 运行内容 | 既有 500GB 运行时盘 | 镜像等可重建内容，不借此推断所有卷都能删除 |

上述是目录模板，不是已经创建的路径。实际 service 名、容器路径、UID/GID 和挂载模式在部署前逐项确定；持久数据沿用 1TB 配置与数据盘的分工。

密钥目录默认 0700、文件默认 0600，由实际读取账号持有；需要组读取时说明原因并采用最小权限。不得以全局可写权限解决容器读写问题。

## 网络与入口

- 数据库和缓存仅内部使用，不新增公网暴露；内部服务不为方便而默认发布宿主机端口。
- 需要 Caddy 代理的本地 HTTP 服务，沿用当前 host 网络 Caddy 的回环上游模式：`127.0.0.1:<HOST_PORT>:<CONTAINER_PORT>`。
- Crawlab 管理页面、业务管理界面、调用方 API、Worker 通信和产物上传下载分别明确访问范围与认证，不把管理端口作为匿名公共入口。
- 现有 Worker 的内网 DNS、HTTPS filer 和 LAN19666 已验收，见下方当前状态。其他设备及未来外网 Worker 的 TLS、认证和传输方式按实际条件另行设计与授权，不据此开放公网端口。
- 不仅凭 UFW 默认拒绝判断 Docker 端口安全；部署验证应覆盖实际转发路径，IPv4 与 IPv6 分别核对。

## 镜像与容器

明确上游版本与可用 digest，自定义镜像固定基础镜像及依赖版本。Crawlab、管理端和 Worker 的版本兼容须核对，不采用可变 latest 作为已确定部署依据。

常驻服务默认候选为 `unless-stopped`；任务子进程不套用常驻重启策略。日志沿用有限轮转要求，新增服务候选默认是 local 驱动、10m、3 份；应用文件日志和原始产物另设保留规则。

默认不使用 privileged、不挂载 Docker socket、不增加无关 capabilities；按镜像兼容性评估非 root、只读根文件系统及 no-new-privileges，例外说明原因。共享 Worker 不被描述为逐任务强隔离沙箱。

重要数据显式挂载，逐项确认镜像声明的匿名卷。服务健康使用可靠业务探针或替代功能验证，容器 running 不等于业务可用。

## 逐模块资源预算

用户要求在各代码模块讨论中持续考虑 CPU、内存、硬盘等资源。M01—M08 的边界与评估项目统一见 [架构](architecture.md)，每模块审阅状态与步骤见 [progress.md](../progress.md)，不另建资源建设任务。代码模块与独立进程／容器分别判断，M03／M04 发布端是否合并运行须结合常驻成本后确认。

预算分别覆盖服务器和每台 Worker：系统及现有服务余量、Master 与实际上游依赖、业务服务、Worker 常驻成本及同时执行的任务峰值；镜像、缓存、主库／索引／WAL、平台结果、原文、日志、临时文件和维护空间一并核算。SQL 主文件上限不能代替整个服务磁盘预算，分布式任务的全局速率不能按节点数重复放大。

在目标节点实际条件未核对前，只记录有假设的估算和待验证范围；应用条数／吞吐目标与容器 CPU／内存限制、磁盘真实可用量分别标注，不能互相当证据。配置资源上限前先明确超限后的限流、排队、拒绝或任务失败行为，避免无界缓冲和过度重试。小规模隔离验证通过后再决定是否扩大并发或增加进程，体验部署已配置初始容器限制；本轮文档整理不调整它们，业务和异设备配额仍待确定。

## 配置与验收

未来 `deploy/<component>/` 保存可复用的非敏感部署声明和参数示例；真实配置在服务器私密目录管理。每个实际部署服务的 README 沿用运维规范六部分：用途与状态、部署与配置、访问入口、数据与密钥位置、常用操作、升级与回退。

声明检查、实际镜像与挂载检查、配置生效和业务验证分别记录。Compose 解析通过不等于业务通过；环境或 Compose 变更不以单纯 restart 代替应用配置。

配置回退、镜像回退与数据恢复分别设计。备份生成、完整性检查和恢复验证分别记状态，不能因完成目录设计就声称已有备份。

## 与原迁移任务的关系

本项目重构不作为云端数据保全和基础迁移的前置条件。本轮不改动旧 Proxypool 快照、不读写云端 Redis、不启动重复采集，也不切换生产来源。

服务器预部署与正式迁移由运维仓库中的 01-C、01-D 独立管理；本仓库文档完成不会自动勾选这些任务。
